## 修订说明（相对初稿）

| # | 修订 | 原因 |
|---|---|---|
| D1 | `children` 存进卡片自己的 `.md` frontmatter，删除 `tree.json` | 初稿里 `children` 既是卡片字段又存在 tree.json，两份真相。放进卡片后卡是自包含的：移动只改两个文件，git diff 可读，符合"卡片是唯一原语" |
| D2 | `ChildEntry` 收敛为 `{ id, layout? }`，删除 `order` 字段 | 数组下标即顺序，`order` 冗余。并且初稿三套结构漏了"看板列里的任务卡"，收敛后看板和列共用一套 |
| D3 | `layout` 变成 ChildEntry 上的可选负载，不再由容器种类决定结构 | §3.1 说普通卡的子卡区也能二维无限，所以坐标不是灵感台专属 |
| D4 | 删除 `type`，改为 `view`；保留 id 固定为 `{000,001,002,003}` | `type` 把"根身份"和"渲染方式"两件事混在一个字段里。拆开后浮卡的定义才自洽：`parent === null` 且 id 不在保留集 |
| D5 | 预制体是 `cards/` 里 `isPrefab: true` 的普通卡，删除 `prefabs/` 目录 | 与 D1 同因，且更贴合"卡片是唯一原语" |
| D6 | `overrides` 改为路径键；阶段三只支持单层预制体，禁止成环 | 字段名无法表达子卡里的覆盖；嵌套预制体是 Godot/Unity 都流过血的地方 |
| D7 | 事件 payload 带 `before` / `after`，增加 `seq` 序号；撤销走命令栈而非日志重放 | 只有字段快照的话撤销做不出来；timestamp 排序在同步时不可靠 |
| D8 | 补 `color` / `due` / `tags` 三个字段 | §3.2 的紧凑卡已经要显示截止日期和颜色，字段表里没有 |
| D9 | 搜索从"优先级三"提到阶段一，先做 MCP 只读工具不做 UI | 搜索是 AI 的刚需，没有 search 的 MCP 基本不可用 |
| D10 | 增加软删除（`trashed` 标记）；MCP server 阶段二起搬进主进程；`core/` 不依赖 Electron | 前者防丢件，后两者防双写和"UI 没写完就没法测" |
| D11 | 多窗口架构定为主进程唯一写者 + 事件广播；跨窗口拖拽延后到骨架稳定之后 | 见 §3。跨窗口拖拽是纯手势成本，模型不需要它 |
| D12 | 删除 `editingBy`，移入后期扩展的预留字段 | 同步未做之前它是死字段 |
| D13 | 事件类型去掉 `child_move`，同父换位改用 `children_order`（带 id 数组前后值）；跨父移动 = `child_remove` + `child_add` | 两种表示法并存会让重放出现两条代码路径。移除加插入本身就完全描述了移动，索引也精确 |
| D14 | 存储去掉 `index.json` 和 `trash.json`，加入 `workspace.json` | 卡片文件名就是 id，索引是多余的；软删除标记在卡片自己身上，「最近删除」扫一遍卡片就够 |
| D15 | `card_create` 与 `card_move` 的 `parent` 允许为 `null` | 桌面是一等去处（浮卡），不能只靠「先建在容器里再拖出来」绕 |
| D16 | 保留根的 `.md` 丢失时会重建，并按 `parent` 收养孤儿卡片 | 丢一个文件就让整个工作区拒绝加载，对美术同学太残酷。注意这只对「根被重建」生效，根还在而 children 少一条仍然报错 |
| D17 | `close()` 会等在飞的写入结束（`waitForIdle`） | MCP 客户端断开时可能还有工具调用正在写盘；不等的话卡片文件写了、事件日志丢了，正好丢掉最需要留痕的那部分 |
| D18 | 不引入构建步骤：Node 直接跑 `.ts`；测试带 `--pool=threads`；`pnpm -r` 加 `--workspace-concurrency=1` | Node 原生剥离类型，省掉 `dist/` 就省掉「源码和产物两套真相」。vitest 默认的 forks 池要拉子进程并接管道 stdio，受限环境里直接 `spawn EPERM`，threads 池不碰这条路径。`pnpm -r` 并发拉子进程同时抓各自输出会撞同一条限制，串行就没事——只有两个包，串行不心疼 |
| D19 | **渲染进程里禁止出现 `-webkit-app-region: drag`**，窗口拖动改由主进程轮询光标实现 | 只要它出现在卡片 DOM 里，CSS 圆角裁剪就整体失效（四组对照实验见 `spike/corner.ts`）。「卡片要好看」是硬需求 |
| D20 | app 用 esbuild 打包（主进程/preload/renderer 三份），不用 Vite | Vite 加载配置文件时会走 `windowsSafeRealPathSync` → `exec`，受限环境里 `spawn EPERM`（本项目最早的 vitest 就栽在这条路上）。esbuild 没这个动作，少一个依赖也少一个坑 |
| D21 | 主进程广播的是**变化后的卡片对象**，不是事件流 | 渲染进程直接替换即可，不需要把事件应用逻辑再实现一遍——两份逻辑一定会漂移。为此给 `ExecuteOutcome` 加了 `changed` / `removed` |
| D22 | 关浮卡窗口 = 隐藏，不是销毁 | 美术点错那个叉子不该丢东西。卡还在树里，main 板能把窗口重新叫出来 |
| D23 | core 增加 `floatingCount()`，新浮卡的窗口位置按它错开 | 原来硬编码 `defaultWindowState(0)`，所以每张新浮卡都叠在同一个坐标——被窗口字符画当场抓出来 |
| D24 | **MCP server 搬进 app 主进程**，以 Streamable HTTP 在 `127.0.0.1` 上对外提供端点；独立 stdio 模式保留 | 两个进程抢一个工作区只能靠排他锁互斥，开了 app 就用不了 AI。搬进去之后 app 是唯一写者，AI 的写入走的是和人拖卡同一条路 |
| D25 | MCP 工具层不直接写 `Workspace`，改成面向 `McpBackend`：读走内存树，写交给宿主 | 否则在 app 里跑的时候窗口收不到广播——「AI 说改了、人的屏幕上没变」，就成两个世界了 |
| D26 | 无状态 Streamable HTTP **每个请求新建一套 server + transport** | SDK 示例的规定动作。复用同一个 transport 时只有第一个请求（initialize）能通，后面的全 500 且响应体为空，症状很有迷惑性 |
| D27 | 后端失败**一律抛错**，不返回 `{ ok: false }` | 返回失败对象时工具会把失败当成功继续往下走（13 个错误路径测试当场全红）。抛错由 `guard` 统一接住，错误码才传得到 AI 面前 |

## 一、项目定位

KankanBan 是一个以卡片为唯一原语的项目管理工具，适用于团队项目和个人项目。对美术策划同学友好，集成 git 图形化操作，AI 通过 MCP 深度参与。同时作为 HCI 课程作业，目标是成为一个以后开发常用的项目管理工具。

核心设计立场：**卡片是唯一的原语，看板不是一种功能，而是卡片在容器里自然长出来的形态。**

- 技术栈：Electron + React + TypeScript + 文件存储 + MCP SDK
- 开发方式：纯 Vibe Coding，AI 为主要开发伙伴。技术选型以"AI 生成准确率"为第一优先级

**一条纪律：`core/` 不 import Electron。** core 必须能在纯 Node 下跑测试、独立启动 MCP server。Electron 只在 `app/` 里出现。

## 二、核心模型

### 2.1 森林结构与保留根卡片

整个系统是一棵森林。父子关系是单向的：父卡持有子卡列表，子卡不知道自己属于谁。移动一张卡就是旧父卡删一条、新父卡加一条。

四张保留根卡片，id 固定，不可删，部分字段不可改。它们都是 `parent === null`，但呈现方式与浮卡不同：

| ID | 名称 | view | 说明 |
|---|---|---|---|
| 000 | main | `main` | 主窗口。应用外壳，三栏（卡片管理器 / git / 设置）。可关窗但不结束应用，可注销工作区 |
| 001 | board | `kanban` | 看板，公有区域，不可删 |
| 002 | inspiration | `plane` | 灵感台，公有区域，不可删 |
| 003 | prefabs | `grid` | 预制体根，公有区域，不可删。通过 main 板打开管理 |

**浮卡的定义**：`parent === null` 且 id 不在保留集中的卡片。每张浮卡对应一个独立系统窗口。

000 也是一张卡片，但它是应用外壳而不是树里的一块区域；它的三个面板是 UI，不是子卡。§7 里"用这张卡片打开所有深度为 0 的卡片"就是 main 卡的一个派生视图（扫描 `parent === null` 的非保留卡）。

### 2.2 卡片字段

```ts
interface Card {
  // 骨架
  id: string
  parent: string | null
  children: ChildEntry[]        // 有序，数组下标即顺序
  title: string                 // 纯文本：窗口标题、看板卡正面、搜索
  content: string               // Markdown 源码，卡片主体
  view?: ViewMode               // 缺省 'row'
  scope: 'private' | 'public'

  // 展示辅助
  color?: string                // 色标，如 '#4A90D9'
  due?: string | null           // ISO 日期
  tags?: string[]

  // 预制体
  isPrefab?: boolean
  prefabRef?: string | null     // 实例指向的预制体 id
  overrides?: Record<string, unknown>   // 路径 → 覆盖值，见 §6

  // 仅浮卡（parent === null 且非保留 id）
  window?: WindowState

  // 元数据
  createdAt: number
  updatedAt: number
  createdBy: string
}

type ViewMode = 'main' | 'kanban' | 'row' | 'column' | 'grid' | 'plane'

interface ChildEntry {
  id: string
  layout?: { x: number; y: number; w: number; h: number; z: number }
}

interface WindowState {
  x: number; y: number; width: number; height: number
  alwaysOnTop: boolean
  minimized: boolean
}
```

关于 `scope`：语义上它是**派生**的——看这棵树挂在哪个根下就知道。但字段照写不误，因为后续同步要靠它做可见性过滤，写下来才能被查询和索引。

| 所在位置 | scope |
|---|---|
| 001 board 的子树 | public |
| 002 inspiration 的子树 | public |
| 003 prefabs 的子树 | public |
| 浮卡的子树 | private |

规则：**拖进公有区域变公有，拖进私有区域变私有，整棵子树跟着变。** 子节点不能单独切换。

### 2.3 顺序与布局

- **顺序 = 数组下标。** 没有 `order` 字段。移动就是 splice。
- **布局 = ChildEntry 上可选的 `layout`。** 只有父卡是 `plane` 视图时才使用。
- 同一张卡从灵感台拖到看板，`layout` 消失，变成列内下标；从看板拖到灵感台，下标消失，变成 `layout`。

### 2.4 视图

视图由父卡的 `view` 字段决定，父卡决定给子卡传什么渲染参数。视图不是卡片类型。

| view | 子卡区形态 | 谁在用 |
|---|---|---|
| `main` | 三栏应用外壳 | 000 |
| `kanban` | 横排的列，列内的卡竖排 | 001，也可给普通卡 |
| `row` | 底部横排 | 普通卡缺省 |
| `column` | 右侧竖排 | 普通卡 |
| `grid` | 格子背包 | 003，也可给普通卡 |
| `plane` | 二维无限平面 | 002，也可给普通卡 |

**没有 `status` 字段。** 一张卡在哪一列，由它的 `parent` 决定。"Done 就是一列"。推论：一张卡不能同时在两列；列的 WIP 上限存在列卡自己的字段上。

### 2.5 公有与私有

默认私有。拖到公有区域（001 / 002）才变公有，拖到私人区域就变私有，否则桌面卡片会很乱。

> 注：多人同步协作已移入后期扩展（优先级最高），当前阶段 `scope` 作为本地逻辑保留，为后续同步做准备。编辑标注、写锁、冲突提示在阶段一至五中不实现，但数据结构上留好位置。

## 三、窗口架构

### 3.1 原则：主进程是唯一写者

渲染进程**永远不直接改数据**。它只发命令：

```ts
ipcRenderer.invoke('cmd', { type: 'card_move', payload: { id, parent, index } })
```

主进程的执行顺序是固定的：

1. 用 commands 层执行命令（纯函数，见 §10）
2. 落盘（写队列串行化，见 §9）
3. 追加事件到 `events.jsonl`
4. 把这次产生的事件**广播给所有窗口**

### 3.2 状态广播

每个窗口的 Zustand store 订阅广播事件并本地应用。因为事件是细粒度的（`field_set` / `child_add` / `child_remove` / `child_move`），每个窗口只需要几十行就能保持一致，不需要写任何 diff 逻辑。

**这同时就是同步层，只是把 WebSocket 换成了 IPC。** 以后做多人协作时，`broadcast()` 换个传输方式即可。事件日志因此在阶段二就产生实际价值，不是超前投资。

### 3.3 窗口的建立与销毁

所有窗口加载同一个 renderer，靠 hash 区分是哪张卡。一个 bundle，一套 store，无 per-window 特判。

```ts
const wins = new Map<string, BrowserWindow>()

function openCardWindow(cardId: string) {
  const w = new BrowserWindow({
    width: 320, height: 240,
    frame: false,
    transparent: true,
    backgroundColor: '#00000000',
    hasShadow: false,
    skipTaskbar: true,
    resizable: true,
    minWidth: 160,
    minHeight: 80,
    webPreferences: { preload, contextIsolation: true, sandbox: true },
  })
  w.loadURL(`${appUrl}#/card/${cardId}`)
  wins.set(cardId, w)

  w.on('moved', () => saveBoundsDebounced(cardId, w.getBounds()))
  w.on('resized', () => saveBoundsDebounced(cardId, w.getBounds()))
  w.on('closed', () => { wins.delete(cardId); closeDesktopWindow(cardId) })
}
```

生命周期规则：

- 深度 0 的卡被创建 → 开窗
- 深度 0 的卡被移进容器 → 关窗（**不是删卡**）
- 浮卡窗口被关闭 → **只是隐藏**。卡仍在树里，main 板的窗口列表可以重新打开。美术不会因为点错叉子丢东西。
- 托盘常驻：左键开 main 板，右键注销工作区 / 退出

### 3.4 跨窗口拖拽（阶段二不做，协议预留）

**模型不需要跨窗口拖拽，只有手势需要。** 阶段二用右键菜单的「浮动到桌面」「收回进容器」跑通 100% 的语义，手势留到骨架稳定之后。

真要做时的关键约束：**HTML5 的 `draggable` / `dragstart` / `drop` 在 Electron 里跨不出窗口**——那是 Chromium 内部的拖拽，OS 层面没有拖拽会话。必须自己用 pointer 事件实现。好在 `setPointerCapture` 能让源窗口在光标移出窗口后继续收到 `pointermove`，协议因此很干净：

1. `pointerdown` → 源窗口发 `drag:begin { cardId }`
2. 主进程进入拖拽态，**只在拖拽期间**每 16ms 轮询 `screen.getCursorScreenPoint()`，算出光标所在窗口与窗口内坐标
3. 主进程向该窗口发 `drag:over { cardId, local }`，窗口高亮可放置区域
4. `pointerup` → 源窗口发 `drag:end`，主进程向最后命中的窗口索取落点，拿到 `{ parentId, index | layout }` 后执行 `card_move`，该关的窗口关掉

坐标一律由主进程计算，绕开多显示器不同缩放比下 `screenX/screenY` 与 `getBounds()` 不一致的坑。

### 3.5 透明窗口的已知坑

阶段二的 spike 专门验证这几条：

- Windows 上 `transparent: true` 配合 `resizable: true` 有 resize 闪烁 / 黑边的历史问题
- 标题栏拖动用 `-webkit-app-region: drag`，交互元素必须加 `no-drag`
- 透明区域**仍然吃鼠标事件**（对卡片来说正是想要的），不要指望点击穿透
- 每个 `BrowserWindow` 默认一个渲染进程，8 张浮卡就是 8 个 Chromium。试试 `app.commandLine.appendSwitch('process-per-site')` 让同源窗口共享进程，并量一下内存
- `skipTaskbar: true`，否则任务栏会被浮卡刷屏

## 四、呈现与交互

### 4.1 三区域布局

每张卡有三个区域：

- **面包屑索引区**：左上角
- **正文区**：Markdown 渲染
- **子卡片区**：底部横排 / 右侧竖排 / 二维无限 / 格子

区域可拖动调整大小。拖到零是**折叠**（本地临时视图状态，进 `view-state.json`），卡片设置里才能永久关闭。折叠后缩成一条窄条，点一下或往上拖就展开。

`main` 和 `kanban` 不显示正文，只显示索引和标题，按各自格式呈现子卡。

### 4.2 紧凑卡与完整卡

区别是显示哪些区域。父卡决定给子卡传什么渲染参数。

- 看板列里 → 紧凑形态：标题 + 几个关键标记（`due`、`color`），自己的子卡完全不露出来
- 灵感台 → 缩略图 + 标题 + 一点点内容预览
- 独立窗口或下钻后 → 完整形态

### 4.3 交互手势

- 单击编辑（点按即可编辑）
- 双击下钻（只显示直接子卡标题，点缩略图进入）
- 长按 / 右键设置菜单
- 拖动移动或组合

像操作系统文件管理器：父级只列直接子项的名字，点进去才看到里面。

右键菜单里放「浮动到桌面」「收回进容器」「设置定时器」「复制为预制体实例」。

**拖出来变窗口是移动不是复制。** 拖进容器变子卡。下钻改变视角不改变树，浮动到桌面才改变树。

### 4.4 面包屑

每个窗口记录当前聚焦的卡片 id，默认是窗口的根卡。点面包屑改聚焦 id，视图重新渲染。**聚焦状态是每个窗口自己的，不同步。**

面包屑不只是导航，它是当前窗口的根路径。点进一张卡之后，它跟原来父卡的关系不变，只是换了个视角看它，树没动。

### 4.5 卡片创建

在任意卡片面板用右键菜单或快捷键创建。快捷键在 main 板的设置栏里管理（全局应用设置，不是工作区设置）。

### 4.6 预制体视觉区分

预制体卡片内部发蓝光；由预制体实例化的卡片外圈发蓝光。

### 4.7 软删除

删除不搬文件：置 `trashed: true`，查询层过滤掉它，恢复就是清标记。

**没有 `trash.json`。** 标记在卡片自己身上，`parent` 也在，所以「最近删除」扫一遍卡片就够了。少一个文件就少一处会不同步的地方。

被删的卡，它的整棵子树会一起从视图里消失——但子卡自己没有 `trashed` 标记，是查询时被祖先压住的。这条区别有几个好用的推论：

- `card_get` 会告诉你这张卡为什么看不见（自己在回收站里 / 某个父卡在回收站里）
- `card_restore` 恢复一张「自己没被删、只是被祖先压住」的卡时**不会假装成功**，而是告诉你是哪个祖先还压着
- 想从回收站的父卡底下把卡捞出来，直接 `card_move` 到别处就行；移出回收站子树会走一条「祖先允许 trashed」的路径
- 恢复一张卡时，如果它的祖先还在回收站里，会给出提醒——否则用户会以为恢复失败了

## 五、事件日志与撤销

### 5.1 定位

**文件是真相，事件日志是派生的流水。** 启动时从文件读树，不从日志重放。日志有三个用途：后续同步、审计、"AI 问最近改了什么"。

撤销**不走日志重放**，走主进程里的命令栈。

### 5.2 事件结构

```ts
interface KkbEvent {
  seq: number           // 客户端内单调递增
  id: string
  clientId: string
  timestamp: number
  cardId: string
  type: 'field_set' | 'child_add' | 'child_remove' | 'children_order' | 'card_trash' | 'card_restore'
  path: string          // JSON Pointer 风格：/title、/children/2/title
  before?: unknown
  after?: unknown
}
```

`before` / `after` 都要写。只有 `after` 的话撤销做不出来。

`seq` 是必须的：光靠 `timestamp` 排序在同步时不可靠。

**每种事件的 payload 形状**（同步端和重放都按这个解析）：

| type | cardId 是 | path | before | after |
|---|---|---|---|---|
| `field_set` | 被改的卡 | `/<字段名>` | 旧值 | 新值 |
| `child_add` | **父卡** | `/children/<下标>` | — | `{ entry, card }` |
| `child_remove` | **父卡** | `/children/<下标>` | `{ entry }` | — |
| `children_order` | **父卡** | `/children` | 旧 id 数组 | 新 id 数组 |
| `card_trash` | 被删的卡 | `/trashed` | — | `true` |
| `card_restore` | 被恢复的卡 | `/trashed` | `true` | — |

`child_add` 的 `after` 里带**整张卡**，`child_remove` 只带条目——不对称是故意的：删除时卡片还在别处（移动就是「从 A 删、往 B 加」），加进来时同步端必须能凭空把这张卡造出来。

`updatedAt` 刻意不发事件：它是本地时间戳，可以从事件的时间推出来，每次都记一条只会把日志变成噪声。它不进事件日志，但撤销时会按记录精确还原，保证撤销之后文件逐字节回到原样。

### 5.3 撤销重做

commands 层每个命令返回**逆命令**，主进程维护命令栈：

```ts
interface CommandResult {
  events: KkbEvent[]
  inverse: Command          // 用于 undo
}
```

删除子树的逆命令要能还原整棵子树（含 content），所以逆命令里内联数据，不要存引用。栈深 100 条，不落盘。

### 5.4 后期同步设计（预留）

- 事件同步，不是状态同步
- 乐观修改，标注谁在改哪张卡
- 冲突时后保存覆盖先保存，并给先保存的人提示
- 冲突提示是窗口外描一圈红线
- 分内容锁和结构锁两层

## 六、预制体

- 预制体根（003）也是一张卡片，并非隐形。
- 预制体本身是 `cards/` 里 `isPrefab: true` 的普通卡，003 的 children 就是这些卡。
- 通过 main 板打开可管理所有预制体，可实例化或直接修改。
- 预制体支持子卡片，像 Godot 场景树一样。
- 实例化预制体需要整棵子树。
- 实例默认跟随预制体，可覆盖字段，可独立为普通卡。
- 改预制体本体锁所有实例；改实例覆盖属性只锁那个实例。

**`overrides` 用路径做键**，不是字段名：

```jsonc
{
  "title": "受伤状态待机",
  "children/2/title": "左臂",
  "children/2/color": "#E0533D"
}
```

路径相对实例根卡，格式同 §5.2。

**阶段三只支持单层预制体**：实例化时整棵子树打散复制成普通卡，子树内部不再保留实例身份。嵌套预制体留到后期扩展——Godot 和 Unity 都在这里流过血。同时必须**禁止预制体成环**（一个预制体不能包含自己），在写入时校验。

卡片需要多几个方法：单独修改该卡片、修改对应的预制体、独立为普通卡片、作为普通卡片复制、作为预制体复制。

通过某个实例卡查找对应预制体时会打开预制体卡片，并显示预制体信息。

## 七、Git 集成

Git 是外部的。指定一个文件夹路径，用图形化界面做 git 操作和 git 树查询。**Git 不是卡片数据层，是 main 板的一种视图。**

- 支持新建仓库、clone、revert 等
- 显示像 VS Code 源代码管理面板
- Clone 和打开文件夹并列；init 是打开后没检测到 git 时的方法
- 提交历史视图，点一条看 diff，右键有 revert、cherry-pick
- 异步操作要有进行中状态
- **错误要翻译成人话**（这是 HCI 层面真正的贡献，写报告时值得单独讲）
- 调 `git` CLI 子进程，不用 libgit2 / dugite
- 状态用 `git status --porcelain=v2` 解析
- **显示 LFS 状态**：哪些文件在 LFS 里、有没有传上去。游戏项目里 .psd / .fbx 十有八九在 LFS，美术最想问的就是"我那张图真的传上去了吗"

AI 自己会用 git，不需要把 git 包成 MCP 工具。但需要一个只读的"获取当前 git 状态"工具。

打开前是空白面板。打开后有两个作用：呈现 git 树和执行 git 操作（之后可能扩展到 svn），以及作为所有浮卡的总入口。

## 九、数据存储

`.kkb` 文件夹像 `.vscode` 一样，和工作区相关的都存这里。默认进 `.gitignore`，可提供选项放开让 `.kkb` 跟 git 走。

只要和工作区相关的都存 `.kkb`，因为默认是 gitignore 的。全局设置另外正常存——快捷键是全局应用设置，不是工作区设置。

```
.kkb/
  cards/<card-id>.md    # frontmatter 存字段，正文存 content。文件名就是卡片 id
  events.jsonl          # 事件日志，每行一个事件
  workspace.json        # 工作区元数据：id、name、clientId、格式版本
  lock                  # 防双写
```

**没有 `tree.json`。** 树结构就活在每张卡的 `children` 里；深度 0 的卡靠扫 `parent: null` 得到。一张卡自包含，所以移动只改两个文件，git diff 可读。

**没有 `index.json`。** 卡片文件名就是 id，路径可以直接推出来，索引纯属多余。

**没有 `trash.json`。** 见 §4.7。

`workspace.json` 里的 `clientId` 是这台安装的标识（事件日志要用它，以后同步也要）。所以 `.kkb` 进版本库时要注意：clientId 是每份检出各自的，不该跟着走。

`view-state.json`（窗口聚焦、折叠比例）是**纯 UI 状态**，阶段二起由 app 层维护，不属于 core。

### 卡片文件格式

键顺序是**固定**的（`card-file.ts` 里的 `FRONTMATTER_KEY_ORDER`），有 golden test 盯着：格式一乱，每次保存都会产生噪声 diff，人看不出改了什么，AI 也会被噪声误导。

```md
---
id: c_0001
parent: "001"
children:
  - id: c_0002
  - id: c_0003
    layout:
      x: 120
      y: 40
      w: 200
      h: 160
      z: 3
title: 主角待机动画
view: row
scope: public
color: "#4A90D9"
due: 2025-06-01
tags:
  - art
  - character
createdAt: 1748000000000
updatedAt: 1748000000100
createdBy: local
---

正文 Markdown……
```

约定：

- 空的可选字段一律不写。文件里只出现有意义的字段。
- 正文为空时不留空行；正文结尾统一一个换行。
- 写入前把 CRLF 规范成 LF。
- 读入时严格校验：`scope` / `view` 的值域、`children` 的形状、`layout` 的每个分量、id 与文件名是否一致。出错要报出**哪个字段、哪个文件、为什么**。
- YAML 用 1.2 core schema 解析，所以 `due: 2025-06-01` 读回来是字符串而不是 `Date`。这一点有专门的测试盯着——它是 YAML 的经典坑。

### 持久化与并发

- 内存里的树是唯一工作副本，落盘是**写队列**串行化的（不要并发写同一个文件）
- 写入用 `write-temp` + `rename` 保证原子性
- **双写保护**：`.kkb/lock` 记录持有者 pid。Electron 主进程持有锁时，独立 MCP server 不允许再打开同一个工作区

## 十、MCP 与 AI

所有人类的操作都通过**同一层 commands** 暴露给 AI。AI 是另一个客户端，人和 AI 走同一套操作层。

**注意措辞**：不是"UI 走 MCP 调自己"。分层是：

```
core/commands   ← 纯函数，唯一的操作层
   ↑        ↑
app/ (UI)   mcp/ (MCP 工具层，面向 McpBackend)
```

UI 直接调 commands，MCP 工具层把 commands 包成工具。这样人和 AI 天然走同一条路，但 UI 不用跟自己讲 JSON-RPC。

### MCP 跑在哪：app 里，用 HTTP 对外

**MCP server 跑在 Electron 主进程里**，以 Streamable HTTP 在 `127.0.0.1:17381/mcp` 对外提供端点
（端口被占用会往后让，实际地址显示在 main 板的设置栏）。

为什么不是 stdio：stdio 要求客户端去**启动**这个进程。可我们需要的是反过来——进程本来就在跑，
客户端连上来。这样 app 成为唯一的写者，人和 AI 看同一份数据，工作区锁也就不存在冲突了。

```
       ┌─────────────── Electron 主进程 ───────────────┐
人 ──→ │ 渲染进程 ──IPC──→ WorkspaceService ──→ Workspace │
       │                        ↑                      │
AI ──→ │ MCP 工具层 ──HTTP──→ McpBackend ─────────────┘
       └───────────────────────────────────────────────┘
```

关键约束：**MCP 工具层不能直接写 `Workspace`**，必须经过 `WorkspaceService`。
否则窗口收不到广播 —— AI 改的东西在人眼前不会变，那就成了两个世界。

所以工具层面向的是 `McpBackend` 这层薄接口：

- **读** —— 直接用内存里的树（只读、立刻）
- **写** —— 交给宿主，由宿主负责落盘和广播

两个实现：app 里是 `WorkspaceService`；独立 stdio 进程里直接调 `Workspace`（没有窗口要广播）。

**独立 stdio 模式保留着**，给「只让 AI 用、不开 UI」的场景。注意那时它和 app 仍然是互斥的
（同一个工作区只能有一个写者），会撞上排他锁。

不是"AI 功能"，而是把人类能做的事暴露成 MCP 工具，AI 自己会组合它们。

MCP 工具的粒度就是"人类操作"的粒度。拖拽这种手势在 MCP 里没法直接表达，应该暴露**意图**，而不是"鼠标按下、移动、松开"三个事件。

**AI 需要"看"到看板才能操作，所以读取类工具比写入类工具还重要。** 只读工具应该返回紧凑视图（一块板的概要，而不是整棵树），因为上下文体量是稀缺资源。

### 阶段一的工具清单（已实现，17 个）

**只读**

| 工具 | 说明 |
|---|---|
| `workspace_info` | 工作区路径、根卡片、浮卡、计数、`lastSeq`。不知道从哪下手时先调这个 |
| `board_overview` | 某块板的列 + 每列的卡（紧凑形态，不含正文）。缺省看 001 |
| `card_get` | 单卡详情，缺省带正文和从根下来的路径，可带直接子卡 |
| `tree_get` | 子树，带深度限制，到顶的节点标 `cut: true` |
| `search_cards` | 按标题 / 正文 / 标签搜，标题命中排前面 |
| `list_cards` | 按父卡列子卡；`parent: null` 列出所有根（含浮卡） |
| `trash_list` | 回收站，最近改动在前 |
| `events_since` | 给定 seq 之后发生了什么 |

**写入**

| 工具 | 说明 |
|---|---|
| `card_create` | 建卡。`parent: null` 建浮卡；建在 kanban 下面缺省就是「一列」 |
| `card_update` | 改字段。只传要改的，传 `null` 表示清除 |
| `card_move` | 移卡 = 改状态。`parent: null` 拖到桌面变浮卡 |
| `children_reorder` | 给全部子卡的新顺序（成员和数量都必须对得上） |
| `children_layout` | 改某个子卡的坐标 |
| `card_trash` / `card_restore` | 软删除与恢复 |
| `undo` / `redo` | 人和 AI 共用同一个撤销栈 |

三条刻意的取舍：

- **`card_purge`（彻底删除）不对外暴露。** 它是撤销 `card_create` 的内部命令；把「不可逆的删除」开放给 AI 收益太低、代价太高。
- **写入类工具都会回一句「刚才发生了什么」**：事件摘要 + `warnings` + 受影响卡片的当前状态。AI 因此不需要每次写完再补一次读取。
- **失败返回结构化错误**（`{ code, message, details }`），不是一句字符串。错误码能让 AI 自己判断该换参数还是该换思路。

服务端的 `instructions` 承担了「先讲清楚这个世界观」的职责——没有 status 字段、数组下标即顺序、保留根、软删除语义。这段文字比任何单个工具描述都重要，因为它省掉的是试错。

阶段三再加预制体工具。**「改预制体本体」和「改实例覆盖」必须是两个不同的工具**，不能混。

权限和审计：人和 AI 走同一套 commands，天然有完整操作日志。审查由 skill 来做。

规则引擎可被 AI 生成。AI 建预制体比建散卡更有意义。

## 十一、开发路线

### 阶段一：核心库 + MCP（不碰 UI）— 已完成

**目标**：卡片树、事件日志、MCP 服务端能跑通，用命令行或测试脚本驱动。

**实际交付**

```
packages/core/src/
  types.ts        数据模型、保留根、视图、事件类型
  errors.ts       KkbError：带错误码 + 人话消息
  ids.ts          id 生成（撞了就重摇）
  card-file.ts    frontmatter 读写 + 严格校验
  tree.ts         纯树操作（祖先/后代/作用域/环保护）
  event-log.ts    只追加的事件日志，容忍被截断的最后一行
  persistence.ts  原子写、写队列、加载、双写锁
  workspace.ts    内存树 + 落盘 + 事件 + 撤销栈 + 原子性回滚
  commands.ts     8 个命令 + 逆命令
  queries.ts      只读投影（紧凑视图，省 AI 的上下文）
packages/mcp/src/
  tools.ts        17 个 MCP 工具 + 服务端 instructions
  server.ts       把工具挂到 McpServer 上
  bin.ts          stdio 入口
```

**测试**：179 个用例全绿（core 152 + mcp 27），`tsc --noEmit` 干净。

```bash
pnpm install
pnpm test             # 两个包加起来 179 个用例
pnpm typecheck
```

用测试覆盖到的、值得单独点名的几件事：

- **golden 文件格式**：序列化结果逐字节比对；键顺序与字段赋值顺序无关；连写两次幂等；CRLF 规范化；`due: 2025-06-01` 读回来必须是字符串而不是 `Date`。
- **撤销是逐字节的**：改字段 → 撤销，文件必须和改动前逐字节一致；重做后必须和改完时逐字节一致。靠的是命令栈里记录的 `updatedAt` 前后值。
- **命令是原子的**：`card_update` 里第二个字段校验失败时，第一个字段也不能被改掉，事件也不能进日志。
- **重启不丢**：关掉再打开，卡片树、事件日志的 `seq`、浮卡的窗口状态都在；没动过的卡片文件逐字节不变。
- **优雅关闭**：`close()` 会等在飞的写入收尾——否则客户端一断，连事件日志一起丢。
- **错误路径**：环形父子、移动到自己子树下、删保留根、显式 id 撞车、引用不存在的卡、同一张子卡挂在两个父卡下、缺保留根。
- **端到端**：真的起一个 MCP server 接一个 client，走完整 JSON-RPC（`InMemoryTransport`），验证 17 个工具都能调、错误码都对、schema 校验能挡住漏参。

**验收标准（全部自动化测试）**

- ✅ 能通过 MCP 工具建卡、移卡、改字段、读树
- ✅ 文件存储的 golden test：写出去的 `.md` 字节级稳定
- ✅ 事件日志能正确记录，`before` / `after` 齐全
- ✅ 每个命令的逆命令能正确撤销，撤销后可重做
- ✅ 错误路径：环形父子、移动到自己子树下、删除保留卡、id 重复

**额外验证（真实 stdio）**：用 PowerShell 往 `node packages/mcp/src/bin.ts` 的 stdin 喂 JSON-RPC，走完整的 stdio 路径：initialize → tools/list（17 个）→ 建两张卡 → 把一张移到「完成」→ 改标题正文 → `tree_get` 读板 → `card_get` 读回路径 `board > 完成`，最后检查磁盘上的 `.kkb` 结构与 7 条事件。确认 Node 24 能直接跑 `.ts`、跨包导入正常、事件确实落盘。

**边界（遵守了）**：不做 UI、不做同步网络层、不做预制体、不做规则引擎、不做 git。

> 说明：vibe coding 的前提下，测试套件就是规格说明书。AI 改坏东西时只有它能拦住。阶段一的验收标准因此全部写成测试——开发过程中它也确实抓到了两个真问题：查询层忘了过滤回收站，以及 `boardOverview` 的缺省板 id 误写成 000（那是 main 板，不是看板）。

### 阶段二：最小 UI + 窗口验证 — 已完成（待人工确认手感）

**目标**：能开窗口、显示卡片、拖拽移动。同时验证 Electron 的透明无边框置顶多窗口行为。

**spike 结论（先做的，因为它决定后面一切）**

| 问题 | 结论 |
|---|---|
| 透明到底生效没有 | **生效**。用「开窗前后的桌面基线逐像素比对」证明：窗口正中在两次截图里完全一致 |
| resize 会不会闪 | 8 个窗口逐个 `setBounds` 全部按预期生效，无异常，内存无跳变 |
| 8 个浮卡多少内存 | **955MB**（8 个渲染进程 648 + 主进程 164 + GPU 98 + Utility 45），每张卡 ≈81MB |
| `process-per-site` 能省吗 | **不能**。开与关都是 11 个进程、Tab 内存 644 vs 648MB |
| 圆角能用吗 | **有坑**：卡片 DOM 里只要出现 `-webkit-app-region: drag`，CSS 圆角裁剪整体失效 |

spike 脚本留在 `packages/app/spike/`：`transparent-windows.ts`（内存/resize）、`calibrate.ts`（坐标标定）、`corner.ts`（圆角对照实验）。

**实际交付**

```
packages/app/src/
  shared/ipc.ts        主进程 ↔ 渲染进程的契约
  main/main.ts         生命周期与接线
  main/windows.ts      窗口管理 + 自己实现的拖动
  main/service.ts      唯一写者：命令、落盘、广播
  main/menu.ts         原生右键菜单与托盘
  main/tray-icon.ts    用像素画出来的托盘图标
  main/debug-capture.ts  窗口字符画（开发期自查）
  main/debug-verify.ts   验收自查
  preload/preload.ts   contextBridge 的唯一出口
  renderer/*.tsx       三区域卡片、紧凑卡、main 板、极简 Markdown
```

**验收标准**

- ✅ 能开 8 个透明无边框窗口，能拖动、置顶
- ✅ main 板建卡 → 自动开窗；右键「收回进容器」→ 窗口关、卡进容器
- ✅ 在窗口 A 改标题，窗口 B 立刻变
- ✅ 关闭浮卡窗口 → 卡还在，能从 main 板重新打开
- ✅ 8 个窗口的内存占用记录下来（955MB / 每卡 ≈81MB）

前四条由 `KKB_VERIFY=1` 自动跑，6/6 通过。第 2 条尤其值得说：界面类的东西很难自动断言，但这条可以——用 `webContents.executeJavaScript` 读渲染进程里的状态即可。

**待人工确认**（机器验证不了）：拖动跟手程度、手动 resize 边缘好不好抓、圆角阴影的实际观感、多显示器/不同缩放比。

**边界（遵守了）**：不做看板和灵感台的特殊布局、不做预制体、不做 git、不做同步、**不做跨窗口拖拽手势**（用菜单代替）。

> 阶段二最有价值的两个产出其实是开发工具本身：**窗口字符画**（`KKB_CAPTURE_AFTER`，把窗口降采样成亮度字符，让读不了图的 AI 也能看出布局）和**验收自查**（`KKB_VERIFY`）。它们当场抓到「两张浮卡窗口叠在同一坐标」。阶段三、四继续用。

## 十三、技术决策记录

| 决策 | 选择 | 理由 |
|---|---|---|
| 框架 | Electron | AI 生成准确率最高，窗口管理成熟 |
| 前端 | React + TypeScript | AI 训练数据最多，类型安全 |
| 状态管理 | Zustand | 轻量，AI 友好 |
| 存储 | 纯文件（Markdown + JSONL） | 文档型数据，不需要关系型数据库 |
| 树结构存放 | 每张卡的 frontmatter | 卡自包含，git diff 可读，无两份真相 |
| 窗口架构 | 主进程唯一写者 + 事件广播 | 8 个窗口零同步逻辑，且就是同步层的预演 |
| 跨窗口拖拽 | pointer 事件 + 主进程轮询光标 | HTML5 DnD 在 Electron 里跨不出窗口 |
| 撤销 | 命令栈 + 逆命令 | 不需要重放整个日志 |
| 同步 | 事件日志（本地），后期扩展为事件同步 | 简单，冲突易定位 |
| 冲突 | 后期扩展，乐观修改 + 后写覆盖 | 小团队场景够用 |
| Markdown | CodeMirror 6 | 成熟，AI 友好 |
| MCP | 官方 TypeScript SDK | 标准，类型安全 |
| MCP 传输 | **Streamable HTTP**（端点跑在 app 主进程里） | stdio 要求客户端启动进程；我们要的是反过来。app 成为唯一写者，锁冲突从根上消失 |
| MCP 工具层的写入 | 面向 `McpBackend`，不直接碰 `Workspace` | 否则窗口收不到广播，AI 改的东西在人眼前不会变 |
| git | `git` CLI 子进程 | 不引入 libgit2 的构建负担 |
| 测试 | vitest | AI 改坏东西时唯一的拦截网 |
| 测试池 | `--pool=threads` | vitest 默认的 forks 池要拉起子进程并接管道 stdio，在受限环境里直接 `spawn EPERM`；threads 池走 worker_threads，不碰这条路径 |
| 构建 | **不构建**，Node 24 直接跑 `.ts` | `erasableSyntaxOnly` 保证语法可剥离；省掉 `dist/` 就省掉「源码和产物两套真相」这个经典坑 |
| app 的构建 | esbuild（三份产物），不用 Vite | Vite 加载配置时会 `exec`，受限环境下 EPERM；esbuild 一个工具把主进程/preload/renderer 全办了 |
| 窗口拖动 | 主进程 60Hz 轮询 `getCursorScreenPoint()` | 不用 `-webkit-app-region: drag`——它会让 CSS 圆角整体失效；而且坐标来源统一（和 `getBounds` 同一套坐标系，不用换算 DPI） |
| 跨进程同步 | 广播变化后的卡片对象 | 渲染进程零事件应用逻辑，不会和 core 漂移 |
| 开发期自查 | 窗口字符画 + `executeJavaScript` 断言 | AI 读不了图，但字符画能看出布局；UI 的验收标准其实大部分可以机械验证 |
| core 的校验 | 手写，不引 zod | 要报出「哪个字段、哪个文件、为什么」这种能直接定位的中文错误。zod 留在 mcp 层管入参 schema |
| 包结构 | pnpm workspace，`core` + `mcp` 两个包 | core 不依赖 Electron，所以能脱离 UI 跑测试、独立起 MCP server |
| 并发 | 写队列 + 原子 rename + `waitForIdle` | 单用户场景够用，但客户端断开那一刻不能丢事件 |

## 十四、风险与边界

**最大风险：范围膨胀。** 阶段一到三已经构成一个完整的课程作业。阶段四的 git 集成如果时间不够，可以降级为"导出 Markdown 文件夹"。

**技术风险：透明无边框多窗口。** 阶段二必须验证。如果发现 `transparent` 的表现不达标，优先考虑降级为不透明圆角窗口（视觉损失有限），而不是硬扛。**兜底方案**是 main 板 + 一个全屏透明"桌面"overlay 窗口承载所有浮卡——拖拽变成纯 DOM 操作，二维平面免费拿到，代价是要自己做点击穿透（`setIgnoreMouseEvents` + mouse-move 转发），而且卡片不再是真正的系统窗口。这个决定**不影响数据模型**，只要保证"卡片 id → 窗口"的映射是一层独立薄封装，随时可以换。

**交互风险：** 三区域布局、拖拽手势、下钻与浮动的区分，这些要实际用一下才能确认。阶段二就找一个人试五分钟。

**数据风险：** 文件写入的并发与原子性。单用户下问题不大，但同步层和本地写入同时发生时需要写入队列 + 原子 rename。双写（Electron + 独立 MCP server）用 `.kkb/lock` 挡住。

**课程作业提醒：** 老师大概率会问"你怎么知道它好用"。阶段五的一手观察比功能列表有说服力。早期发现的问题改起来便宜。

**多人同步移除后的影响：** 当前阶段 `scope` 作为本地逻辑保留，事件日志为后续同步预留接口。编辑标注、写锁、冲突提示这些 UI 元素在阶段一至五中不实现，但数据结构上留好位置。
