# KankanBan 开发文档（修订版 v7）

> 本版相对你给我的 v1 做了修订，**改动清单见 §0**。未列入 §0 的章节保持原样。
> 技术栈：**Tauri 2 + React + TypeScript + 文件存储 + MCP SDK**。

### 当前正文编辑实现（2026-10-16）

普通卡片窗口和管理器的正文统一由 `CardBodyEditor` 承载。普通模式的阅读与文字输入共用 `Markdown`／`RichImageBody` 同一组排版节点，启停输入只改变可编辑状态，不替换布局；Markdown 输入直接更新源文本并呈现格式，支持 Ctrl+B／Ctrl+I／Ctrl+Shift+X。源码模式与输入焦点分开管理，只有模式按钮可以切换源码／排版，点击外部、右键、失焦、Escape 只结束输入。右键按下先保存当前标题／正文，失败保留草稿和编辑状态；原事件继续交给窗口拖动，不消费整段手势。图片和表格始终复用原位的对象编辑、移动、缩放与单元格操作。铅笔／橡皮统一为左键画／擦、右键退出，右键继续拖动时交给窗口；灵感台沿用已配置的按键功能。

正文右下角的工具从上到下分为模式按钮、图片／表格胶囊、铅笔／橡皮胶囊三行。工具通过 Portal 独立浮动，定位使用正文区域的 border box，不占正文流、不减去滚动条宽度，也不能溢出到子卡区。仅正在输入的文字区域保留原生拖选；未编辑时拖正文移动窗口，单击才进入编辑，并以按下命中点恢复光标。进入编辑仅以轻微背景色变化提示，排版和坐标不变。窗口标题和空白区域继续使用窗口拖动规则。普通卡片、扩展和管理器的右键可从输入框、对象等内部开始移动窗口，移动跨越原有 6px 阈值才生效；灵感台保留自身拖动设置。子卡区的新建按钮常驻 DOM，随子卡区折叠／展开以同一 140ms ease 淡出／淡入，折叠时禁止点击与聚焦。

磁盘与 MCP 中的正文仍为原有 Markdown，不存 HTML 或编辑器 JSON。`formatted-editor-model.ts` 使用现有排版的 source map 映射原生选区，保存逻辑光标，防止已隐藏的 Markdown 分隔符吞掉后续输入；图片、表格为受保护的完整对象。`rich-editor-model.ts` 的 ProseMirror 文档模型用于格式操作和格式化复制，保留未修改正文块的原始文本；不能用整个正文 DOM 的 `textContent` 代替源文本。两种模式使用同一滚动视口，以源字符偏移和可见锚点恢复选区及视图，不直接套用另一种排版的 `scrollTop`。主题沿用 `.kkb-markdown` 与现有 `--md-*` 参数，编辑器不能增加第二套字体或文字留白、整体移动图片／表格／涂鸦坐标。

## 0. 修订说明

### v7（多窗口落地修订）

用户定案：「**关闭卡片不影响任何结构！可以在 main 中重新打开！**」
这一条把不变量 W 从"**等价**"改成"**子集**"，是本版最大的一处修订 ——
旧写法下"关窗"只能靠改树实现，与新语义直接冲突。

同时，多窗口的**状态所有权**（v6 一直挂着的"多窗口状态所有权"待决项）定案为
**方案 A：main 单写者**。参考项目 `sticky-tauri` 在这一点上给不出先例 ——
它没有持久化，状态全在 Rust 的 `AppState` 里，窗口只是薄视图；而 KankanBan 每个 webview
都是独立的 JS realm，各建一份会话，两边都写就会让 `events.jsonl` 的 seq 分叉。

| I-47 | `updatedAt` **从来没有人维护**：建卡时写一次就再也不动，于是 `cards/*.md` 里"创建时间"与"更新时间"永远相同，`show` 里也一样 —— 一个骗人的字段（用户报的正是这个） | 定义成**派生量** = "指向这张卡的最后一条事件的时间"，由 `applyEvent` 统一推进（事件里 `cardId` 指谁就是谁被改）。顺带两处：`createCard` 改成**只读一次时钟**（原来读两次，新卡一出生就 `updatedAt > createdAt`）；`field_set` 明确拒绝 `/updatedAt`，免得留一个静默失效的旋钮。**反转了 §10 原决定**，理由见那一行 —— §2.3 / §10 |
| I-48 | 让 `updatedAt` 会动之后，炸出三个连带缺陷：① `card_delete` 的快照比对会把**一次正常的崩溃恢复**判成"数据损坏"（`writeState` 先写卡片文件，那里 `updatedAt` 已是删除后的值，而快照记的是删除前的）；② `undoEvent` 只看状态与这一条事件、**看不到日志**，撤销推不回旧值，`undo(events) === 上一状态` 在 `updatedAt` 上不成立；③ 已存在的日志与卡片文件都是**老语义**写下的（`updatedAt` 恒等于 `createdAt`、事件也没有 `prevUpdatedAt`），新代码一算重放一致性就报红 —— 在你那份真实工作区上是 5 张卡 | ① 快照比对里把 `updatedAt` 与 `deleted` **一起归一化**（同一个理由：卡片文件领先于 tree.json；而且它是派生量，本来就不是独立证据）；② `Envelope` 增加 `prevUpdatedAt`，由事件自己带上旧值 —— 与 `from` / `fromIndex` / `removedEntry` 同一类；③ `materializeUpdatedAt(state, events)` 在**打开工作区时**按整条日志重算一遍（派生字段的权威本来就是日志），`undoLast` 也调它兜住老日志的撤销。改完 22 条红回到 0（除一条与本次无关的）—— §4.1 / §4.2 / §10 |

## 一、项目定位

KankanBan 是一个以卡片为唯一原语的项目管理工具，适用于团队项目和个人项目。对美术策划同学友好，集成 git 图形化操作，AI 通过 MCP 深度参与。同时作为 HCI 课程作业，目标是成为一个以后开发常用的项目管理工具。

核心设计立场：**卡片是唯一的原语；看板不是一种功能，而是卡片在容器里自然长出来的形态。**

开发方式：纯 Vibe Coding，AI 为主要开发伙伴。技术选型以"AI 生成准确率"为第一优先级。

**唯一声明的例外**：托盘与原生菜单不是卡片（属于 OS 层）。除此之外任何"界面上的东西"都必须能表达成一张卡。

## 二、核心模型

### 2.1 森林结构

整个系统是一棵森林。**深度为 0 的卡片就是独立窗口。**

父子关系是**单向**的：父卡持有子卡列表，子卡不知道自己属于谁。

> **v1 的自相矛盾已修正**：v1 在 §2.3 给卡片加了 `parent` 字段，与此处冲突。
> 本版明确：**`parent` 不落盘**，它是加载时从 `tree.json` 构建的**内存派生索引**，
> 只用于 O(1) 反查（AI 读树、`kkb://` 反链所需的场景）。移动一张卡就是
> 旧父卡删一条、新父卡加一条，随后重建索引。

### 2.2 四个内置卡

| ID | 名称 | layout | 说明 |
|---|---|---|---|
| 000 | main | `tabs` | 主控板。**强制存在**的窗口，可注销工作区。**v7：它同时是唯一写者，所以关掉它等于结束这次会话**（见 §7.1 的修订） |
| 001 | board | `columns` | 看板，公有区域，全局唯一，不可删。**直接子节点是列卡** |
| 002 | inspiration | `plane` | 灵感台，公有区域，全局唯一，不可删 |
| 003 | prefabs | `grid` | 预制体根，全局唯一，不可删，通过 main 板打开管理 |

四者**都是普通卡片**，只是带内置渲染器。它们的 `type` 均为 `null`（见 §2.5 终止规则）。

固定 ID 不允许删除，也不允许修改会破坏内置语义的字段（如 `id`、`type`）。

**「强制存在」怎么落实（v6 补）**：`openSession` 默认调 `ensureBuiltins`，
用**普通事件**（`card_create` + 固定 id）把缺的补上。

- **不做"内置卡另存一处"的特殊处理**：它们就是普通卡片，因此照样进日志、
  照样能被 `replay` 重建、照样走同一套落盘路径（§9.1）
- **幂等**：已经存在的不动，也不多写事件。重开工作区不会又建一遍
- **留了一个口子**：`openSession(root, { builtins: false })`。它只该用在一种场合 ——
  想构造一棵**最小树**来测 core 自身的机制（那时四张内置卡只是噪音）。
  真实入口一律不传，于是"工作区里一定有内置卡"这句话成立
- 这条当初漏掉时症状很隐蔽：`read_tree({scope:'public'})` **永远返回空数组**，
  看起来像"过滤生效了"，其实是**公有根卡根本不存在**

**内置卡表**：`src/core/builtins.ts` —— §2.2 与 §2.5（渲染分派第 1 步）、
§2.6（公有区域恰好是哪几棵）、§2.7（不可删）**共用同一个来源**。

**main 的语义（本轮确定）**：main 自己不展示正文；它下面挂三个子节点（卡片管理器 / git / 设置），
以**标签页**形式呈现，点击标签页展示**那个子节点**的内容。

> 这条与"卡片是唯一原语"是一致的：三个面板本身就是卡，main 只负责把它们组织成标签页。
> 也解释了为什么 main 必须有子节点才有意义 —— 空 main 板就是一个空白标签页容器。

**prefabs 的语义（本轮确定）**：纯格子排列（见 §2.4 的 `grid`）。

**board 的语义（本轮确定）**：直接子节点是**三张列卡**；渲染时**跨一层投影** ——
自身与直接子节点的正文都不显示，显示的是**孙节点**。详见 §2.5.1。

### 2.4 ChildEntry

子卡的布局数据存在**父卡的 `children` 条目**里，不存在子卡自己身上。
同一张卡从灵感台拖到看板，坐标消失、变成列内序号——**条目在移动时被重写**。

```ts
type CardId = string;

// 【顺序型】横列 / 数列 / 标签页 / 格子背包 / board 的列
// 全部由"顺序"表达，不需要坐标 —— 格子背包是【自动流式】，也归在这里（本轮确定）
type OrderedEntry = { id: CardId; order: number };

// 【坐标型】二维无限平面（灵感台）
type PlaneEntry = { id: CardId; x: number; y: number; w: number; h: number; z: number };

// 【无布局信息型】普通卡
type PlainEntry = { id: CardId };

type ChildEntry = OrderedEntry | PlaneEntry | PlainEntry;
```

**只有两种"带布局信息"的条目形态：顺序型与坐标型。** 这是把"格子背包"确认为自动流式
之后的结果 —— 它不需要格子坐标，因此不必新增类型。

**条目形状由「父卡的 `layout`」决定，不是条目自带判别字段。**
加载时必须依据父卡的 `layout` 校验条目，形状不匹配视为数据损坏并记录诊断。

### 2.4.1 layout → 条目形状

| layout | 用在哪 | 条目 |
|---|---|---|
| `tabs` | 000 main | `OrderedEntry`（标签页顺序） |
| `columns` | 001 board | `OrderedEntry`（列的顺序）；**列卡自身再用 `OrderedEntry` 存列内卡片顺序** |
| `grid` | 003 prefabs、格子背包 | `OrderedEntry`（自动流式，按 order 排放） |
| `plane` | 002 inspiration | `PlaneEntry`（坐标 + 层级） |
| `ordered` | 横列 / 数列 / 列卡 | `OrderedEntry` |
| `plain` | 普通卡默认 | `PlainEntry` |

> `columns` **不需要新的条目类型**：两层都用 `OrderedEntry`，一层表达列顺序、一层表达列内顺序。
> 这也是"直接子节点是三张列卡"这个选择的好处 —— 不需要给条目加 `column` 字段。

**不变量 O（v6 补，实现期被随机化测试逼出来的）**：同一顺序型父卡内，`order` **严格递增**；因此**按 `order` 排序 == 数组顺序**，§2.4.1 的"按 order 升序渲染"与事件用数组下标寻址
**不会给出不同结果**。

> **`order = 插入下标` 是错的。** 这个最直白的写法会坏：往 `[A@0, X@1, Y@2]` 插入得到
> `[A,X,B@1]`，再插到第 2 位就是 `[0,1,2,1]` —— 按 order 排序变成 `[A,X,B,Y]`，
> **与数组顺序真的分叉**（不是"理论上可能"，是 `test/order-invariant.test.ts` 跑出来的）。

**正确写法是取相邻两个 `order` 的中点**（首位减 1、末位加 1）：

- 一次插入只产生**一条事件**，因此**撤销仍是"一步"**。
  若改成"插入后给整列重新编号"，一次拖动会炸出 O(n) 条事件，`undoLast` 就退化成
  "连撤 n 次"，与 §4.3 断言二的粒度对不上
- `order` 由此获得**独立于数组下标的意义**：它是**为多人同步预留的可合并排序键**
  （§11 优先级一），数组下标只负责本地寻址 —— 两者是两件事，不是同一事实存两遍
- 代价：反复往**同一个**间隙里插会让数值细分下去（0.5 → 0.25 → …）。
  实现里对"间隙已经不可再分"**直接抛错**而不是静默产出两个相等的 order
  （静默的话渲染顺序会取决于排序算法是否稳定）。重新编号留作后续

### 2.5 呈现方式

`type` 指向一张**呈现定义卡**；呈现方式是该卡上的 `layout` 字段。

```ts
type Layout = 'tabs' | 'columns' | 'ordered' | 'grid' | 'plane' | 'plain';
```

### 2.5.1 `columns`（board 的看板布局）

**跨一层投影**：不渲染自己与直接子节点的正文，而是把孙节点铺出来。

```
自身 content                 不渲染
直接子节点（列卡）
  ├─ 列头   = 该列卡的 title
  ├─ 该列卡自身 content       不渲染
  └─ 列体   = 该列卡的子节点，按 order 升序，以【紧凑卡】呈现（§3.2）
```

要点：

- 层级固定为 **board → 列卡 → 任务卡** 三层
- **列卡的正文只是"不在本视图渲染"，不是"没有"**（本轮确定）：双击下钻该列卡后，
  它是一张**正常的两块内容的卡** —— 正文 + 列内卡片，与其它卡无异（§3.4）
- 列卡本身是普通卡（有 id、有 title、可被引用、可下钻），只是在本视图里只用它的 title 当列头
- 任务卡以紧凑形态呈现，它自己的子卡完全不露出来（§3.2）

**拖放到 board**（本轮确定）：把卡拖到 board 上时**自动落到落点所在的列**——
列卡基本占满窗口，所以命中的列就是落点所在的列；落点恰好落在列与列之间时，取水平距离最近的列。
**不允许任务卡直接落在 board 层级上**（那会让它变成一列）。

**这条在 core 里也有防线（v6 补）**：`moveCard` 拒绝把卡直接移到看板层级。

- **只拦"从外面移进来"**：看板下已有的列卡之间重排序、以及"新建一张卡到看板下"（那正是新建一列）都允许
- 判"是不是看板"用 `rendererOf`，所以对**用户自己用 `type` 指向 columns 呈现定义卡**做出来的看板同样生效
- 实现期这条防线**立刻抓到一个真实违规**：一条既有测试把预制体根卡 `003` 移到了看板 `001` 下面 ——
  那确实会让它变成一列。测试已改成移到非看板父卡下

> **一个连带的删除后果**：删除一张列卡会级联删掉整列的任务卡（§2.7 级联删除）。
> UI 的"将删除 N 张卡"确认在这里尤其重要 —— 删一列可能是几十张卡。

分派规则（**这就是终止规则，链长恒为 1，不会递归**）：

1. `card.id` 是内置 ID（000/001/002/003）→ 用内置渲染器
2. 否则 `card.type` 非空 → 读该卡的 `layout` 决定呈现方式
3. 否则 → `plain`（正文 + 子卡横排）

写入时校验：**`type` 只能指向内置卡，或指向一张 `type === null` 的卡**。这样不存在
"type 卡自己还有 type" 的链，渲染器一次解析即可。

> **v1 的冲突已修正**：v1 §2.3 说 `type` **就是**呈现方式，§2.4 又说"呈现方式由卡片字段决定、
> 不是卡片类型"。本版统一为：`type` 是**引用**，`layout` 才是呈现方式字段 —— 两句话都成立。

> **推论（v6 补：实现时我和测试同时理解错过）**：卡**自己的 `layout` 不决定它自己被怎么渲染** ——
> 分派第 2 步读的是**被 `type` 指向的那张卡**的 `layout`。所以一张普通卡自己写着
> `layout: 'columns'`、`type` 为空时，它渲染成 `plain`。
>
> 卡自己的 `layout` 只影响两件事：**①别人 `type` 指向它时**；**②它的子卡条目形状**（§2.4.1）。
> 想让一张卡长成看板，正确做法是让它的 `type` 指向一张 `layout: 'columns'` 的呈现定义卡，
> 或者干脆就是内置卡 `001`。

**`type` 与 `prefabRef` 是正交的两件事**（v1 未说明）：

| | 回答的问题 | 作用域 |
|---|---|---|
| `type` | 我**怎么被渲染** | 单张卡 |
| `prefabRef` | 我的**字段从哪继承** | 实例 → 预制体 |

两者可同时存在，互不影响。

### 2.6 公有与私有

**`scope` 是纯派生函数，不落盘、也没有写入入口。**

```ts
function scopeOf(cardId: CardId): 'public' | 'private' {
  const root = rootAncestorOf(cardId);                       // 深度 0 祖先
  return (root === '001' || root === '002') ? 'public' : 'private';
}
```

**实现落位（v6 补）**

| 东西 | 落在 | 说明 |
|---|---|---|
| 内置卡表（id / 名称 / `layout` / 是否公有） | `src/core/builtins.ts` | §2.2 与 §2.5、§2.6 **共用一个来源**，不各写一份 |
| `scopeOf` / `rootAncestorOf` / `pathFromRoot` | `src/core/scope.ts` | 纯函数 |
| `parentIndexOf` / `locateEntry` / `isInSubtree` | `src/core/indexes.ts` | §2.1 的派生索引；视图模型、段落、窗口集合共用 |

> **`rootAncestorOf` 遇到环或断链不抛错**：它会被读路径频繁调用（列表、权限判断），
> 在那儿因为一棵坏子树整体报错，代价太大。走到头的那张卡就是它自己的根。
> 坏数据由加载期校验与 `assertInvariantW` 在**写入/加载**时拦，不在这条热路径上拦。

- 公有区域**恰好**是 board（001）与 inspiration（002）—— 由内置卡表声明，不是用户可设的字段
- 一张卡从私有树移到 board/inspiration 子树下 → 它的深度 0 祖先变成 001/002 → 变公有
- 移回私有树 → 变私有

所以"变公有 / 变私有"**完全由树位置决定**（本轮依你答复"只能靠移动"确定）。
它既不该占一个字段位，也就不存在"改了字段但树位置没动"这种不一致状态。

**推论（刻意的收紧）**：用户**无法**创建自己的公有区域，除非把卡移进 001/002。
否则"公有"会退化成一个人人可设的开关，公有区域必然失控。

> 多人同步已移入后期扩展。当前阶段的这条派生规则**就是同步层要用的规则** ——
> 落地时不需要改数据布局，只需把 `scopeOf` 用于过滤。

### 2.7 删除

- **子树级联**：删除一张卡连同其整棵子树。UI 必须显示将删除的卡片数并要求确认
- **"显示张数"需要一个无副作用的预览**（v6 补）：`deleteCard` 的返回值只能**事后**知道，
  来不及给确认框用。所以操作层另给一个 `subtreeSize(session, cardId)` —— 只数不删。
  有一条测试专门断言**预览数与实际删除数一致**：否则确认框就是在骗用户
- **软删除**：写入 `card_delete` 事件，**事件携带整棵子树快照**，因此可撤销
- **落盘形式（v6 定）**：给子树每张卡的 `deleted` 字段打上 `true`，**文件仍留在 `cards/`**。
  同时把它们从 `children` 里摘掉，使其不再被任何父卡引用。
  这样重启后加载不会让已删的卡复活，而撤销只需把快照放回去 —— **撤销全程不碰磁盘**
- 物理文件清理放到 compaction 阶段，不在删除操作里同步做
- 内置卡（000/001/002/003）不可删

**`moveCard` 的一条补充规则（v6 补）**：**同父重排不改布局数据**。
坐标型父卡（`plane`）里的同父重排只改数组位置，所以 `moveCard` 在那种情况下
**沿用旧条目的 x/y/w/h/z，不要求调用方传坐标**。

- 一开始是无条件要求传坐标，症状是"在灵感台里拖一下卡片就报缺坐标" —— 而那本来是合法的重排
- 但**从别处移进** plane 父卡仍然必须给坐标：编一个默认坐标就是"卡跑到了我没放的地方"

> v1 完全没有删除语义。本版按"级联 + 软删 + 可撤销"落笔。
> **如果你要的是"提升子卡为根"而不是级联，见 §14。**

### 2.8 不变量

**不变量 W′（v7 修订）**：`openWindows ⊆ desktopCards(state)`，且桌面卡片里有 main 时 `openWindows` 必须含 main

```
desktopCards(state) = { card | parent === null ∧ ¬deleted }   // 窗口**候选**：能不能有窗口由树决定
openWindows                                                   // **实际**开着窗口的卡（view-state.json）
```

> **v6 的旧 W 写的是"等价"**（窗口集合 ≡ 未删除的根卡），那意味着"关窗"只能靠改树实现。
> 用户定案：「**关闭卡片不影响任何结构！可以在 main 中重新打开！**」
> —— 于是权威拆成两半：**树说"能不能有窗口"（窗口 id 就是根卡 id），视图状态说"现在有没有窗口"**。

- **`¬deleted` 不能省**（v6 补）：软删除的卡不再被任何 `children` 引用，于是从 `parent` 索引看
  它"没有父卡"，会被误判成一张可以有窗口的卡 —— 已经删掉的东西会**在桌面上重新冒出来**
- 把一张深度 0 卡拖进容器 → 它有了父 → **必然**从窗口集合里消失（子集关系自动滤掉）
- 把一张子卡"浮动到桌面" → `parent` 变 null → 它**成为**桌面卡片，
  但**不会自动开窗** —— 要显式「提出到屏幕窗口」。**候选 ≠ 已开**是这条修订的核心
- 关窗 = 把它从 `openWindows` 里去掉：不产生事件、不进日志、不撤销、也不动一张卡的任何字段
- 违反 W′ 的写入在 core 层直接拒绝

**不变量 U**：`replay(空, events) ≡ 当前状态`（见 §4.3）

**不变量 C（v5 新增，实现阶段补）**：`children` **不出现空数组** —— 有键 ⟺ 至少有一个子卡。

- 这张表一旦出现空壳（`{ p: [] }`），`undo` 与"前缀重放"就会在**语义相同、形状不同**上分叉，
  §4.3 断言二永远差最后一点。实现时就是这么被测试逼出来的
- 也因此，"一张卡没有子卡"与"这张卡不在 `children` 里"是**同一件事**，不需要两种表示

这三条都要写进阶段验收标准，它们是最容易漏又最好测的约束。

**W′ 的实现（v7 修订，v6 版见下）**：`src/core/windows.ts` 给出三个纯函数：

```ts
desktopCards(state): CardId[]                    // 窗口**候选**：{ card | parent === null ∧ ¬deleted }，按 id 排序
openWindowSet(state, remembered): CardId[]       // **实际**开着的：remembered ∩ desktopCards，再把 main 补上
wantedCardWindows(state, openIds, renderedId)    // 写者要同步出去的真窗口（去掉 main 与本窗口正在显示的那张）
windowTransition(before, after)                  // { opened, closed }，给平台层去开/关真窗口
assertInvariantW(state, context, open?)          // 护栏：中间状态被写坏时当场炸，而不是等下次加载
```

开窗 / 关窗是**视图动作**，所以落在 `view-state.ts`：

```ts
openWindow(view, windowId)      // 加入 openWindows（幂等：已开着返回同一个引用）
closeWindow(view, windowId)     // 移出 openWindows；**保留**该窗口的位置 / 聚焦；拒绝关 main
```

> **排序是刻意的**：窗口集合会被拿去前后做差集，不排序的话同一个集合会产出不同数组，
> diff 出来一堆假变化。
>
> **`assertInvariantW` 与加载期校验刻意重叠**：那边防的是磁盘上的坏数据，这边防的是
> "core 自己算错了"。一条不变量只在入口校验，中间被写坏就没人管。
>
> **`closeWindow` 为什么拒绝 main**：§14 方案 A 把 main 定为**唯一写者**，
> 关掉它需要先定"谁接管"（参考项目的答案是"管理器关了就收掉所有便签，应用退出"）。
> 这一轮没有接管机制，所以宁可直接报错，也不让工作区变成没人写盘的状态。

## 三、呈现与交互

（保持 v1，此处仅摘录，无修订）

### 3.1 三区域布局
面包屑索引区（左上）、正文区（Markdown 渲染）、子卡区（底部横排 / 右侧竖排 / 二维无限）。
区域可拖动调整大小；拖到零是**折叠**（本地临时视图状态），卡片设置里才能永久关闭。
board 与 inspiration 不显示正文，只显示索引与标题。

**实现约定（v6 补）**

| 项 | 约定 | 理由 |
|---|---|---|
| 区域名 | `breadcrumb` / `content` / `children` | 与 `view-state.json` 的键一一对应 |
| 折叠 | **尺寸为 0 就是折叠**，不另存一个布尔 | 两个状态由一个输入源推出，不会互相矛盾 |
| 窗口 id | **就是该窗口根卡的 id** | §2.8 W′ 已经保证"开着的窗口必是桌面卡片"，再发一套 id 是冗余 |
| 渲染分派 | 内置 id → 内置渲染器；`type` 非空 → **被指向那张卡**的 `layout`；否则 `plain` | §2.5.1 |
| 三种形态 | 内置 `tabs`/`columns`/`grid` no-op（还没做）；`plane` 与 `plain` 同形 | 阶段三才补内置渲染器 |

**子卡区的排布由渲染器推出（v6 补）**

| 渲染器 | `childrenMode` | 容器 | 出处 |
|---|---|---|---|
| `grid` | `grid` | `.child-grid`（`auto-fill` 网格） | §2.2 prefabs「纯格子排列」 |
| `plane` | `plane` | `.child-plane` + 每张卡按 `x/y/w/h` 绝对定位，`z` 交给 CSS `zIndex` | §2.2 inspiration「二维无限」 |
| 其余 | `row` | `.child-row`（底部横排） | §3.1 默认 |

> **`plane` 的坐标是数据，不是视图状态**：`PlaneEntry` 的 x/y/w/h 进 `tree.json`（§2.3），
> 所以渲染层只负责照着摆，不参与计算。
>
> **已知缺口**：从**别处**拖一张卡进 plane 父卡需要坐标，而 UI 还没有"坐标级拖拽"
> （拖放只给数组下标）。core 会明确拒绝并说明原因，不会编一个默认坐标 ——
> 编了就是"卡跑到了我没放的地方"。

### 3.2 紧凑卡与完整卡
区别在于显示哪些区域。看板列内显示紧凑形态；独立窗口或下钻后显示完整形态。
**父卡决定给子卡传什么渲染参数。**

### 3.3 交互手势
单击编辑 / 双击下钻 / 长按或右键菜单 / 拖动移动或组合。
像文件管理器：父级只列直接子项，点进去才看到里面。
**拖出来变窗口是移动不是复制；下钻改变视角不改变树，浮动到桌面才改变树。**

**空放不发事件（v6 补）**：落区收到 `drop` 时如果**没有正在被拖的卡**，必须什么都不做。

- 实现期最初写成 `draggingId ?? child.id`，会在空放时把这张卡"移到它自己身上"。
  结果虽然是个无变化的移动，却**照样产生一条事件** —— 日志噪音，还多出一步没意义的撤销
- 这条之所以值得写下来：它在真机上几乎碰不到（空放很难发生），
  但**交互测试一碰就现形**，属于"只有真派发事件才能发现"的那类问题

**"单击编辑"与"双击下钻"怎么共存（v6 补）**

不需要"等 250ms 看有没有第二次点击"那种计时器：

```
click 1  → 进入编辑态
click 2  → 已经在编辑态，忽略
dblclick → 下钻（同时清掉编辑态）
```

- 关键在于**下钻会清掉编辑态**：即使中间那一下进入了编辑，双击之后也不留残余
- 编辑中的卡 `draggable={false}` —— 否则选字会变成拖放
- 三处可编辑：**紧凑卡标题**（子卡区 / 看板列内）、**当前那层面包屑**（= 聚焦卡的标题）、**正文区**
- 点**非当前**层的面包屑是"聚焦过去"，不是编辑 —— 两者靠 `isCurrent` 区分

**多行编辑的提交键**：正文是 Markdown 多行文本，所以**单独 Enter 是换行，Ctrl/Cmd+Enter 才提交**；
标题是单行，Enter 直接提交。Esc 一律取消。

**右键新建（§3.5）**：建完**立刻切进标题编辑态** —— 否则用户要先接受一个叫"新卡片"的东西再改名，
多一步且容易留下没改名的卡。

**右键菜单与删除确认（v6 补）**

右键只是**开菜单**，不直接执行动作 —— 菜单条目按目标卡现算：

| 目标 | 菜单条目 |
|---|---|
| 普通卡 | 新建子卡 / **删除这张卡**（危险色） |
| 内置卡（000–003） | 只有 新建子卡（§2.7 内置卡不可删，**不给删除入口**） |
| 面板空白处 | 对**当前聚焦的卡**开菜单 |

- 落在子卡上时 `stopPropagation`，免得窗口那一层再开一次菜单
- 删除走**应用内确认框**而不是 `window.confirm`：桌面 webview 对原生对话框支持不一致，
  而且应用内面板才能被交互断言覆盖
- 确认框里必须出现**将删除的张数**（§2.7）
- **菜单分两组**（v6 补）：`新建子卡` / `呈现方式`（一个标题 + 五个选项，当前那项打勾） / `删除这张卡`
- **"呈现方式"里刻意没有 `plane`**：改成平面需要每张子卡一个坐标，而坐标是**数据** ——
  凭空编一个就是"卡跑到了我没放的地方"（core 的 `reshapeEntries` 也是这么拒绝的）。
  界面上要提供它，得先有**坐标级拖拽**，那是独立的一步
- 改呈现方式**必须走 `setLayout` 而不是 `setField('/layout')`** —— 见 §4.1 的 `layout_change`；
  有一条测试专门验"从菜单改完 layout 之后工作区仍然能重新加载"
- **菜单要夹进视口**（v6 补）：绝对定位的菜单点在窗口右下角会被裁掉、条目够不到。
  位置钳制写成**纯函数** `clampMenuPosition(pointer, size, viewport)` ——
  jsdom 里 `getBoundingClientRect` 全返回 0，靠"渲染后测量再改位置"是测不出来的；
  菜单尺寸则由条目数估出（估算值必须与 `.menu-item` 的 CSS 对得上，对不上最坏是夹偏一点）
- **Escape 一律关浮层**（菜单 / 删除确认 / 内联编辑），且**绝不顺手执行动作** ——
  有测试专门断言"Escape 关掉确认框之后卡没被删"

**撤销出口（v6 补）**：界面既然有删除，就必须有撤销 —— 否则 §2.7 的"可撤销"只存在于 MCP 工具里。

- **Ctrl/Cmd+Z**，外加状态栏一个按钮（没得撤时**禁用**，而不是点了之后回一句"没得撤"）
- **焦点在文本框里时不抢 Ctrl+Z**：那时它是"撤销打字"，属于编辑器的本分。
  抢走会让"刚打错一个字想撤回来"变成"整张卡的标题被撤没了"
- 撤销会**关掉所有浮层**（菜单 / 确认框）：否则菜单会指着一张已经不在原位的卡

**§2.8 的一个崩溃路径（实测炸出来的）**：把"新建这张卡"这一步撤销掉之后，
窗口的根卡就**从 `cards` 里彻底消失**了，`viewOf` 当时直接抛错、整次渲染被打断。

- 现在的契约：**`viewOf` 返回 `CardView | null`**。根卡不存在时给 `null`，界面显示空态
- 注意**软删不算**：软删的卡仍在 `cards` 里（只是 `deleted: true`），`viewOf` 照样有内容。
  两条路径要分开 —— 写测试时我第一版就把它们混了
- **返回空态 + 「关闭这个窗口」**（v7 补）：无边框窗口没有关闭按钮，
  所以空态里必须留一个出口，否则用户会被困住；正常的清理仍由写者的窗口对账完成

### 3.4 面包屑
每个窗口记录当前聚焦的卡片 id，默认是窗口的根卡。点面包屑改聚焦 id，视图重渲染。
**聚焦状态是每个窗口自己的，不同步。** 面包屑的本质是"当前窗口的根路径"，不是导航历史。

**聚焦失效的回退规则（v6 补）**：聚焦的卡**被删掉、不存在、或属于别的窗口**时，
一律退回**本窗口的根卡**。

- "属于别的窗口" 也要退回，因为面包屑定义为"本窗口的根**路径**" ——
  聚焦到窗口外，面包屑就说不通
- 软删除会把整棵子树的 `children` 一起摘掉，所以"往上找最近的活祖先"通常一步就走到头，
  直接退回根卡；但规则本身写成"逐级上溯再兜底"，这样以后改动删除语义也不会漏

### 3.5 卡片创建
任意卡片面板用右键菜单或快捷键创建。快捷键在 main 板"设置"栏管理（全局应用设置，非工作区设置）。

### 3.6 预制体视觉区分
预制体卡片内部发蓝光；由预制体实例化的卡片外圈发蓝光。

**实现（v6 补）**：由已有字段直接推出，**不额外存储**（§2.3 的权威原则）：

```ts
glowOf(fields) = fields.isPrefab ? 'prefab'          // 内部发光
               : fields.prefabRef !== null ? 'instance'  // 外圈发光
               : null
```

- 和折叠、正文可见性、子卡排布一样，**标记由 `viewOf` 算出**，渲染层只负责套类名
  （`.glow-prefab` / `.glow-instance`），另加 `data-glow` 方便断言与调试
- **`isPrefab` 优先于 `prefabRef`**：一张卡可以既是预制体又是别人的实例（预制体里嵌预制体），
  那时"我是预制体"是更强的身份，按内发光处理；两种光同时存在时内发光叠在外发光之上
- 内发光用 `box-shadow: inset`、外发光用普通 `box-shadow` —— 视觉上一眼分得开

> **未落实**：§2.3 说 `isPrefab`「**仅 003 子树内为真**」，这条**没有强制**。
> 强制它需要在移动时校验（一张卡被移出 003 时怎么办？自动清掉标记？禁止移动？），
> 而文档没说 —— v7 起如实记在 §14「仍然开着的两件事」里，不再假装已清空。

## 四、事件日志

### 4.1 事件结构

```ts
type Envelope = {
  id: string;
  seq: number;          // 单调递增，用于一致性协议（§4.2）
  clientId: string;
  timestamp: number;
  cardId: CardId;
  /**
   * 这条事件**之前** cardId 那张卡的 `updatedAt`（新卡为 undefined）。
   * v7 新增：`updatedAt` 是派生量（= 指向这张卡的最后一条事件的时间），
   * 但撤销推不出来（`undoEvent` 看不到日志），所以旧值必须由事件自己带上 ——
   * 与 `from` / `fromIndex` / `removedEntry` 同一类（§4.3 断言二）。
   * 旧日志没有它：那时撤销保持当前值（§0 的 I-48）。
   */
  prevUpdatedAt?: number;
};

type CardEvent = Envelope & (
  // 字段级快照：带旧值，否则无法撤销
  | { type: 'field_set'; path: string; from: unknown; to: unknown }
  // 子卡列表：用 cardId 寻址，不用数组下标（下标在插入/删除后会指向错误的卡）
  | { type: 'child_add';    parentId: CardId; entry: ChildEntry; index: number }
  | { type: 'child_remove'; parentId: CardId; entry: ChildEntry; index: number }
  // 改条目本身（顺序型改 order、坐标型改坐标）。from 与 entry 成对，撤销才能把旧顺序放回去
  | { type: 'child_update'; parentId: CardId; entry: ChildEntry; from: ChildEntry; index: number }
  // 跨容器移动：必须同时携带"从旧父摘下的条目"和"按新父形状重建的条目"
  // fromIndex / index 缺一不可：plain 父卡的子卡顺序**只由数组下标表达**
  // v6（I-11）：`index` 一律是"被移动的卡在**最终**列表里的位置"。
  //              同父重排与跨父移动**不需要分开换算** —— 最终位置恰好等于
  //              "在摘除之后的列表里插入的下标"（后者就是前者的定义）。
  //              唯一的差别是合法范围：同父时摘除后列表短一个。
  //              越界一律夹到最近的合法位置（拖过头就落到末尾），不抛错。
  | { type: 'card_move'; cardId: CardId; fromParent: CardId | null; toParent: CardId | null;
      fromIndex: number | null; removedEntry: ChildEntry | null;
      addedEntry: ChildEntry | null; index: number | null }
  | { type: 'card_create'; cardId: CardId; parentId: CardId | null;
      entry: ChildEntry | null; fields: Record<string, unknown> }
  // 软删除：携带整棵子树快照以支持撤销
  // removedIndex 与 card_move.fromIndex 同理，撤销要按原位放回
  | { type: 'card_delete'; cardId: CardId; parentId: CardId | null;
      removedEntry: ChildEntry | null; removedIndex: number | null; subtree: unknown }
  // v6（I-34）：改 layout **必须连带重写子卡条目**，所以它不能走 field_set
  | { type: 'layout_change'; cardId: CardId; from: Layout; to: Layout;
      before: ChildEntry[]; after: ChildEntry[] }
);

**字段路径是平铺的**：`/title`、`/content`、`/prefabRef`。
（v1 的例子 `/fields/due` 暗示有个 `fields` 包裹层，与 §2.3 的平铺字段不符，已去掉。）

**四条关键修正**（v1 的事件结构无法支撑它声称的用途）：

1. **`field_set` 带 `from`** —— v1 只有 `{path, value}`，是**只有新值**，撤销无从下手
2. **子卡用 `cardId` 寻址** —— v1 用 `/children/2/title` 这种数组下标，只要前面发生过一次
   增删，重放就会写到**另一张卡**上，属于静默错误
3. **`card_move` 显式携带两个条目** —— v1 的 `child_move` 无法表达"跨容器时条目形状要变"
   （坐标 → 序号），重放端不知道按哪种形状重建
4. **凡是"摘除"型事件都必须带上它在旧父卡里的下标**（v5 新增）——
   `card_move.fromIndex`、`card_delete.removedIndex`，外加 `child_update.from`。
   这条是**实现阶段用逆运算测试逼出来的**：`removedEntry.order` 只在顺序型父卡里能反推原位，
   `plain` / `plane` 父卡里原位**无处可存**，撤销就会把卡放错位置。
   v2 的 P0-2 只给 `field_set` 补了 `from`，**当时漏掉了另外三个**。

### 4.2 一致性协议（WAL）

`events.jsonl` 当作 **write-ahead log**，文件是状态，两者分工明确：

```
写入顺序：
  1. append event 到 events.jsonl + fsync
  2. 应用到内存
  3. 原子写状态文件（写临时文件 + rename）
  4. 记录 lastAppliedSeq

启动恢复：
  1. 读 tree.json 与其中的 lastAppliedSeq
  2. 重放 events.jsonl 中 seq > lastAppliedSeq 的尾部事件
  3. 磁盘状态与日志重新一致
```

这样崩溃不会留下"半写"状态：事件一旦落盘，重启后一定被重做到文件里。

**compaction**（后期再做）：把当前状态写成新快照、截断已应用的日志。
当前阶段**不做**，日志无限增长是可接受的。

**部分写入下的幂等要求**（v6 补，实现阶段被崩溃测试逼出来）

`writeState` 是**多文件**写入（每个 `cards/<id>.md` 一个，外加 `tree.json`），
一次 commit **不是**单文件原子操作 —— 所以崩溃一定会留下跨文件不一致的中间态，
最常见的是"`cards/*.md` 已经写新、`tree.json` 还停在旧水位线"。
此时重放尾部事件会**再次应用**那些已经部分生效的事件。因此：

- **重放必须对"同一事件应用两次"幂等。** `card_create` / `field_set` 天然幂等；
  `card_delete` **刻意不检查"是不是已经删过"** —— 加了那个检查，一次正常的崩溃恢复
  会被判成数据损坏（实现时确实这么炸过）
- `card_delete` 的快照比对把 `deleted` **一律按 `false` 看**（快照按定义是删除前的视图），
  理由同上
- 重复删除的**面向用户**的拦截放在操作层（`workspace.deleteCard`），不在 reducer

> 这是一条容易被忽略的约束：写入次序（cards 先、tree.json 后）保证了**不丢数据**，
> 但它同时**故意**制造了短暂的不一致。两件事必须成对设计。

### 4.3 验收性质（可执行）

v1 的"事件日志能正确记录并重放"不可测。改为**五条**断言（与 §10 阶段一一致）：

```
replay(空, events) === 当前状态          # 一、重放一致性
undo(events)       === 上一状态          # 二、撤销正确性
杀掉进程于任意写入点 → 重启后状态一致      # 三、崩溃一致性
write(读(工作区)) === 工作区             # 四、存取往返
能通过 MCP 工具建卡、移卡、改字段、读树     # 五、MCP 通路
```

> §4.3 原文只写了三条，缺"存取往返"与"MCP 通路" —— v6 补齐，与 §10 对齐。

### 4.4 撤销与日志的关系（v6 补）

§4.3 的 `undo(events) === 上一状态` 只说了撤销是**事件序列的函数**，
**没说撤销怎么落盘**：日志是 append-only 的，而撤销要让某条事件"不再算数"。

**当前实现的约定**：撤销 = 把状态回滚到"去掉最后一条事件"的样子，
然后**原子重写整个日志**。写入次序与正向操作**相反** —— **状态先写、日志后截断**：

- 崩在中间时最坏结果是"这次撤销丢了"（日志还留着那条事件，重启会重放它），
  磁盘状态与日志始终互相自洽
- 反过来（先截日志、再写状态）会留下"日志更短、状态却已经前进"的矛盾，
  而那种状态**无法自愈** —— 没有任何信息能告诉恢复逻辑该往后退多少

**已知取舍**：这破坏了"日志只追加"的性质。更彻底的做法是追加**补偿事件**
（撤销 `field_set` 就再发一条把值换回来的 `field_set`），但 `card_delete` 的撤销
**无法用现有事件表达**（缺一个 `card_restore` 之类的事件类型），需要先扩充事件模型。
本轮没做，**留作后续决定**。

## 六、Git 集成

Git 是外部工具：指定一个文件夹路径，用图形界面执行 git 操作与查询 git 树。
**Git 不是卡片数据层，是 main 板的一种视图。**

- 支持新建仓库、clone、revert 等；界面像 VS Code 源代码管理面板
- clone 与"打开文件夹"并列；init 作为打开后未检测到 git 时的方法
- 提交历史视图：点一条看 diff，右键有 revert / cherry-pick
- 异步操作要有进行中状态；错误要翻译成人话
- 打开前是空白面板；打开后一是呈现 git 树与执行操作（之后可能扩到 svn），
  二是作为所有深度 0 卡片的入口
- AI 自己会用 git，不需要包 MCP 操作 git；可能只需要一个只读的"获取当前 git 状态"工具

### 6.1 `.kkb` 与 git 的关系（v1 的冲突已解决）

**`.kkb` 整体默认且推荐不进 git。** 理由：

- `events.jsonl` 是 append-only，每步操作都追加 → git diff 噪音极大，多人**必然冲突**
- `tree.json` 是整文件 JSON → 两人各改一处**必然冲突**
- §4.2 的"后写覆盖"冲突模型**对 git merge 完全不适用**（git 不会给你"后写覆盖"）

v1 的"可提供选项放开让 .kkb 跟 git 走"会同时踩上这三条。**该选项推迟到同步层落地之后再提供。**

**协作通道改为显式导出**：需要把卡片内容交给别人时，用"导出 Markdown 文件夹"（单向），
而不是让状态文件参与 merge。这也正是你自己在风险节里写的降级方案。

git 真正服务的是**工作区里用户自己的文件**（美术资源、文档等），那部分天然无冲突。

## 七、Main 板

强制存在的窗口（卡 000）。**v7 修订**：它是唯一写者（方案 A），所以
「可关闭窗口但不结束应用」这条**已经作废** —— 关掉 main 就没有人写盘了。
现在的行为照参考项目：main 一关，Rust 收掉所有卡片窗口，应用退出。
要恢复"关掉 main 还继续跑"，得先有"写者接管"机制（谁能接手、怎么交接）。

- 空白状态支持：打开上次未注销的项目 / 打开过去的项目 / clone / 打开文件夹
- 打开后呈现 git 树、执行 git 操作，并作为所有深度 0 卡片的总入口
- 三栏：卡片管理器、git、设置；窗口列表与 git 是独立侧边栏
- 托盘常驻：左键开 main 板，右键有注销工作区、退出
- **单工作区**，不支持多个；只要 main 板有托盘即可

### 7.3 窗口生命周期（v1 缺失，本版补）

- **启动**：总是打开 main（000）；其余窗口按 `view-state.json` 恢复上次会话中打开的集合
  （默认开启恢复，可在设置里关掉）
- **恢复时校验**：若某卡当前 `parent !== null`（已被拖进容器），**不恢复窗口**（符合不变量 W′）
- **新建**：浮动一张卡 → 打开窗口
- **上限**：不设硬上限，但恢复集合由 `view-state.json` 决定，不会无限增长

> 默认"恢复上次会话"**已确定**（本轮答复）；设置里可关掉。

**实现（v6 补）**

`view-state.json` 的 `openWindows` 从 v7 起就是"**现在**开着哪些窗口"的权威（树只管"能不能开"），配这几个纯函数：

```ts
openWindow(view, id) / closeWindow(view, id)     // 开 / 关；关不碰树，也不清该窗口的位置与聚焦
openWindowSet(state, remembered)                 // 实际开着的 = remembered ∩ desktopCards，再补上 main
restorableWindows(state, remembered, {restore})  // 这次启动该开哪些
wantedCardWindows(state, openIds, renderedId)    // 写者要同步出去的真窗口（§14 方案 A）
```

- **"总是打开 main"** 落在 `openWindowSet` 里：桌面卡片里有 `000` 时它恒在结果中
- **恢复时校验直接落在 `desktopCards` 上** —— 它已经是"未删除的根卡"，
  所以"被拖进容器"（`parent !== null`）与"已删除"两种失效情形**自动被过滤掉**，
  不需要另写判断，也不会出现"窗口集合与不变量 W′ 打架"
- `restore: false`（设置里关掉）时只给 main
- 旧格式的 `view-state.json` **v1 的 `openWindows` 一律丢掉**（见 I-43）：那个字段的语义变了 ——
  v1 记的是"候选有哪些"，v2 记的是"用户真的开着哪些"。丢掉不报错，也不影响 `windows`（位置 / 聚焦照读）
- `rememberOpenWindows` 在集合没变时**返回同一个引用**：调用方是 React 的 `setState`，
  每次都返回新对象会让它白重渲染

> **"多窗口状态所有权"已定案（v7）**：选**方案 A —— main 单写者**。
> 于是"启动恢复"不再卡住：写者算出 `wantedCardWindows` 交给 Rust 的 `sync_card_windows`
> 多退少补（开窗 / 关窗 / 崩溃残留三种情况走同一条路径收敛）；卡片窗口是**只读镜像**，
> 改动一律 `emit` 给 main，main 提交后广播 `kkb:changed` 让所有镜像整体重载。
>
> 所以"同一套逻辑只有一份"这条仍然成立：镜像转发出去的是 `Intent`（一个**数据**），
> main 执行它用的还是同一个 `runIntent`。不存在"镜像版语义"。
>
> **仍有的一处权宜**：`wantedCardWindows` 把"main 正在**显示**的那张卡"排除在外，
> 否则同一张卡会同时出现在 main 和一扇卡片窗口里。等 `tabs` 语义定案
> （main 渲染 000 的标签页，§14「仍然开着的两件事」）这条权宜自然消失。
>
> **随之而来的限制**：main 是唯一写者，所以它关掉时 Rust 会顺手收掉所有卡片窗口、
> 应用退出（§7.1 旧稿写的"可关闭窗口但不结束应用"在方案 A 下**不成立**了，
> 要恢复它得先有"写者接管"机制）。core 里 `closeWindow` 直接拒绝关 main，挡的就是这个。

## 八、数据存储

`.kkb` 文件夹像 `.vscode` 一样，与工作区相关的都存这里。**默认进 `.gitignore`**（见 §6.1）。

**落实方式（v6 补）**：打开**全新**工作区时确保 `<root>/.gitignore` 里忽略了 `.kkb/`。

- 写入的是**带标记的块**（`# KankanBan 工作区状态…` + `.kkb/`），所以下次能认出"已经加过了"
- **幂等**：已有 `.kkb/` 就一个字都不改；用户自己写成 `.kkb` 或 `/.kkb` 也算数
- **用户原有规则一行不动**，只在末尾追加；原文件不以换行结尾时先补一个换行，免得把块粘到上一行
- **只对全新工作区做一次** —— 否则每次开会话都去读一遍，还会覆盖用户后来的手动修改
- 没有 `.gitignore` 就建一个：§8 说的是"默认进"，不是"如果已经有才进"

```
.kkb/
  cards/<card-id>.md     # frontmatter 存字段，正文存 content
  tree.json              # 树结构：存在性、父子关系、子卡顺序、布局坐标；含 lastAppliedSeq
  events.jsonl           # WAL + 操作历史，每行一个事件
  prefabs/<prefab-id>.md # 预制体定义
  view-state.json        # 窗口位置/大小、折叠比例、聚焦 id、openWindows（现在开着哪些窗口）—— 纯本机
```

**`tree.json` 的字段（v6 补）**

```jsonc
{
  "version": 1,
  "lastAppliedSeq": 9,
  "cards": ["c1", "c2"],        // ← 存在性权威，见 §2.3
  "children": { "c1": [ /* ChildEntry… */ ] }
}
```

> `cards` 这一项是**被实测逼出来的**：`cards/` 目录里的文件不能当"哪些卡存在"的依据。
> 撤销一次建卡会把卡从状态里去掉，而"删文件"没法与 `tree.json` 原子完成 ——
> 崩在中间会留下"文件已删、结构还说它在"，工作区直接打不开。
> 反过来，留着孤儿文件又会让**被撤掉的卡在重开时复活**。
> 分工定死：**存在性归 `tree.json`，字段归 `cards/*.md`**，孤儿文件直接忽略
> （`writeState` 会顺手清理，且把清理放在 `tree.json` **之后** —— 两个方向的崩溃都自洽）。
> 旧格式（没有 `cards` 字段）按"文件即权威"读，向后兼容。

**权威分工见 §2.3。** 一句话：`tree.json` + `cards/*.md` 是可读状态；
`events.jsonl` 是写入意图与恢复来源；`view-state.json` 纯本机、不进 git、不进日志。

全局设置（含快捷键）另外按平台惯例存放，**不属于工作区**。

## 九、MCP 与 AI

### 9.1 Core API 与 MCP 的关系（v1 措辞已修正）

v1 说"人和 AI 走同一套 MCP"。这个说法会误导实现——UI 若真要穿过 MCP（一个外部协议边界）
再回到 core，纯属浪费。

**正确表述**：

```
        ┌──────────────┐
        │  core 操作 API │  ← 唯一权威的操作层（TypeScript 函数）
        └──────┬───────┘
     ┌─────────┴─────────┐
   React UI           MCP 适配器  ──→  AI agent
（直接调用）      （把同一批操作暴露成 MCP 工具）
```

人和 AI 共享的是 **core 操作 API**；MCP 只是它的一个适配器。

#### 这是一条硬约束，不是措辞偏好

**core 操作层不得 import React，不得依赖任何浏览器/DOM 全局，也不得依赖任何 Node API。**
它必须是一批能在**纯 Node** 与**浏览器 webview**里都能 `import` 并调用的普通 TypeScript 函数。
三个理由：

1. **MCP 适配器要调它** —— 适配器跑在 Node 侧，不在 webview 里。若 core 与 React 缠死，
   MCP 就只能去驱动 DOM，等于把所有操作逻辑写两遍。
2. **React UI 也要调它** —— UI 跑在 Tauri 的 webview 里，**那里没有 Node**。
   所以"不依赖浏览器"与"不依赖 Node"必须**同时**成立，这才叫平台无关。
3. **阶段一的验收断言要能在无 GUI 环境跑**（见 §10）—— 重放一致性、撤销正确性、
   崩溃一致性全是纯数据行为，只要 core 干净就能在命令行验证。

> **这条是被实测打脸的**：实现期 core 里有 4 行 Node 依赖（`node:path` 的 `join`、
> `node:crypto` 的 `randomUUID`、`node:fs`），Node 侧的 138 条测试**全绿**，
> 直到搭 UI 才发现 webview 里根本加载不了。
> 于是把约束写成**可执行的测试**（`test/platform-neutral.test.ts`）：
> 扫 `src/core/**`，任何 `from 'node:` / `import 'react'` / `window.` / `document.` /
> `process.` 都会让测试失败并指名道姓报出文件与行号。

**平台 API 的落位**（core 里一律没有）：

| 层 | 内容 | 位置 |
|---|---|---|
| 接口 | `FsOps`（同步，9 个原语） | `src/core/storage/fs-ops.ts` |
| 注入点 | `injectFsOps` / `defaultFsOps` | 同上 |
| Node 实现 | `nodeFsOps` + bootstrap | `src/node/` |
| 内存实现 | `MemoryFs`（测试、预览、以及 webview 的写回缓冲） | `src/platform/` |
| webview 实现 | `AsyncFsOps` over Tauri IPC | `src/webview/` |

### 9.2 读模型（v1 缺失，本版补）

你自己指出"读取类工具可能比写入还重要"——很对，但 v1 没给形状。**强制分页**是重点：
AI 读整棵大树会直接爆上下文，而这恰是它最需要的能力。

```ts
read_tree(scope?: 'public' | 'private', maxDepth?: number, cursor?: string)
  → { nodes: TreeNode[], nextCursor?: string }

read_card(id: CardId, includeChildren?: boolean) → CardSnapshot

list_children(parentId: CardId, cursor?: string, limit?: number)
  → { entries: ChildEntry[], nextCursor?: string }

search(query: string, limit?: number, cursor?: string)
  → { items: CardSummary[], nextCursor?: string }
```

默认 `maxDepth` 取浅值（例如 2），深读必须显式指定。

### 9.3 其余原则（保持 v1）

- 所有人类操作都作为 MCP 开放给 AI agent；AI 是另一个客户端
- 不是"AI 功能"，而是把人类能做的事暴露成工具，AI 自己组合
- MCP 工具的粒度 = "人类操作"的粒度；暴露的是**意图**，不是"鼠标按下/移动/松开"
- AI 可以操作预制体，但**"改预制体"与"改实例"必须是两个工具**
- 权限与审计：人机同一套操作层，天然有完整操作日志
- 审查由 skill 来做；规则引擎可被 AI 生成
- AI 建预制体比建散卡更有意义

### 9.4 MCP 工具目录（v6 补）

§9.2 只给了读模型的形状，**写工具清单从来没出现过** —— 而"原则"翻译不成函数，
适配器实现必须有一张确定的表。按 §9.3 的粒度原则定为**九个**工具：

| 工具 | 类别 | 说明 |
|---|---|---|
| `create_card` | 写 | 建卡，可选挂在父卡下 |
| `set_field` | 写 | 改一个字段（`/title`、`/content`、`/layout`…）；`/id` 与 `/deleted` 不允许 |
| `move_card` | 写 | 移卡；`toParentId: null` = 浮动到桌面 |
| `delete_card` | 写 | 级联软删除，返回 `deletedCount` 让人先看到量 |
| `undo` | 写 | 撤销最后一次改动 |
| `read_tree` | 读 | 根卡及若干层子卡，默认 2 层，到顶的节点标 `truncated`；`scope` 可只看公有/私有；分页 |
| `read_card` | 读 | 一张卡的全部字段与正文；`includeChildren` 可连子卡条目一起返回 |
| `list_children` | 读 | 直接子卡条目，强制分页（`nextCursor`） |
| `search` | 读 | 标题 + 正文子串搜索，不含已删除的卡；**也分页**，结果按 id 稳定排序 |

> **三个读接口的分页游标走同一套校验**（`workspace.ts` 的 `parseCursor`）：
> 非法 cursor **抛错**，而不是当成 0 静默从头读 —— 后者会让 AI 以为"读完了"，
> 实际上一直在读第一页。
>
> **`create_card` 刻意不暴露 `id`**：§9.3 的粒度是"人类操作"，没有人会手打卡片 id。
> 内置卡由 core 在初始化时创建（阶段三），不由 AI 建。

**写工具故意不拆细**：没有 `set_title` / `set_content`，只有 `set_field`；
没有"拖动开始 / 拖动中 / 拖动结束"，只有 `move_card`。AI 表达的是**意图**，不是手势。

**实现约定**：适配器用 MCP SDK 的**低层 `Server`**，不用高层的 `McpServer.registerTool` ——
后者的 `inputSchema` **只接受 zod**，会把 JSON Schema 过一道有损转换；
而 MCP 协议在 `tools/list` 里传的本来就是 JSON Schema。用低层 Server 才能**声明即所见**，
也因此不必为工具目录引入 zod。

**错误约定**：工具失败回 `isError: true` + 原因文本，**不让异常炸掉整个会话** ——
一次调用失败不该让连接断掉。业务错误（卡不存在、会成环）从 core 原样透出，
不在适配器里 catch 成空结果：AI 需要看到"为什么不行"才能改。

### 9.5 Rust 侧承担什么（v6 补）

**只做 webview 做不到的那部分 I/O，不含任何业务判断。**

Tauri 的 webview 里没有 Node，所以 core 跑在那儿；但"把字节真正写到盘上"这件事
webview 做不到 —— 尤其 **fsync**（§4.2 的 WAL 承诺"事件落盘后才算数"最终就靠它兑现）。

于是 Rust 侧只有 14 个命令，全是文件原语 + 窗口原语：

```
fs_exists / fs_read_file / fs_read_dir / fs_mkdirp / fs_write_file
fs_rename / fs_append_file / fs_fsync / fs_remove / workspace_root
card_window_labels / open_card_window / close_card_window / sync_card_windows   ← v7 多窗口
```

三条约定：

- **全部 `async fn`** —— Tauri 的同步命令跑在**主线程**上，在那里做文件 I/O 会卡住 UI
  （这条来自 `sticky-tauri` 原型：同步命令里建窗直接死锁）
- **`fs_write_file` 不保证原子** —— 原子性由 core 侧"写临时文件 + rename"负责，
  Rust 只提供原语。放在哪一层是有意的：崩溃点必须能被测试插进去
- **业务逻辑一行都不要下沉到 Rust** —— 否则同一套规则会有两份实现，
  UI 与 MCP 就会漂移（§9.1 想避免的正是这个）

### 9.6 命令行：抛开 UI 验后端（v7 补）

**入口**：`npm run cli -- <命令>`，或直接 `node src/cli/main.ts <命令>`。

存在的理由只有一个：**UI 是验证后端时最不该挡路的一层**。窗口、渲染、IPC 任何一环出问题，
都会让你分不清"后端错了"还是"界面错了"。CLI 把链路砍到
「一条命令 → 一次 core 调用 → 一次 WAL 写入」，于是后端对不对一眼可见。
它**不新造语义**：`create` 就是 `createCard`，`edit --layout` 就是 `setLayout`，
`check` 就是 `replay` + `assertInvariantW`。

```
create <id> [-p <父卡>] [-t <标题>] [-c <正文>] [--layout <方式>] [--type <卡>]
edit <卡> [-t <标题>] [-c <正文>] [--layout <方式>] [--set /字段=JSON]…
move <卡> [-p <父卡>] [-i <下标>]        # 不给 -p = 浮动到根（= 提出到桌面）
delete <卡> / undo
tree [--depth N] / show <卡> / ls [<卡>] / find <文字> / path <卡> / windows / log
check                                    # 不变量 U（重放一致）+ W′（窗口集合 ⊆ 桌面卡片）
```

四条约定：

- **位置参数是卡片 id**（`create Card1` → id 就叫 `Card1`）；其余命令里引用可以写 id，
  也可以写**唯一标题**，重名时**拒绝猜**并列出候选
- **默认动应用自己那个工作区**（CLI 必须与 UI 看同一份数据），`--workspace <目录>`
  或环境变量 `KKB_WORKSPACE` 可改；实际路径每次都打在**第一行**，免得"改了哪份"靠猜
- **惰性开会话** —— 看用法 / 命令打错 / 参数不合法，这三条路径**一个字节都不写盘**
  （开会话会 `ensureBuiltins`，那是会写盘的）
- **`--json`**：输出单个 JSON 对象，失败也走 stdout，靠**退出码**表达失败
- **已知限制：值以 `-` 开头要绕一下** —— `edit Card1 -c "- 第一步"` 会被判成"选项缺少值"，
  改成 `--content=- 第一步` 即可。放宽值判定能让它直接可用，代价是**拼错的选项会被静默当成值收下**；
  当前选择是保持严格 + 给出可照抄的报错（这条限制**没有**断言保护，是有意留着的）

> **为什么 `--set` 的值必须是 JSON、而字符串要走 `-t` / `-c`**：`--set /title=123`
> 这种"自动转型"正是 I-44 那个把工作区写死的入口。现在写侧会拒，但 shell 里
> `--set '/title="文字"'` 的双引号又常被吃掉（PowerShell 需要写成 `\"`），
> 所以字符串字段老老实实用 `-t` / `-c`。
>
> **交付时另跑过真进程**：`test/cli.test.ts` 是无头断言，真进程那一层单独实跑过一次
> —— 就是那次实跑抓出了 §0 的 **I-44 / I-45 / I-46**。这类洞在 UI 上很难被发现，
> 在命令行里一次就露出来，这正是它存在的意义。

## 十、开发路线

> **修订**：v1 的风险排序与阶段顺序不一致——风险最高的两件事（窗口层、三区域交互）
> 都不在阶段一，而 v1 自己说"早期发现的问题改起来便宜"。
> **窗口层已在 `sticky-tauri` 原型里验证过**（见 §13），所以下面只在阶段二前插一个垂直切片。

### 阶段一：核心库 + MCP（不碰 UI）

**交付物**：卡片数据结构与文件读写；树操作（增删改查、移动、父子关系）；
事件日志生成与重放；WAL 一致性协议；MCP 工具列表与实现。

**验收标准**（v1 的"重放正确"改为可执行断言）：

```
replay(空, events) === 当前状态
undo(events)       === 上一状态
杀掉进程于任意写入点 → 重启后状态一致
write(读(工作区)) === 工作区          # 存取往返
能通过 MCP 工具建卡、移卡、改字段、读树
```

**边界**：不做 UI、不做同步网络层、不做预制体、不做规则引擎。

> **这五条断言全都应该能在无 GUI 环境跑**（例如 `node --test`），这是 §9.1 那条硬约束的由来。
> 前四条是纯数据行为，第五条打的是 MCP 适配器——适配器本来就跑在 Node 侧，不在 webview 里。
> 只要 core 不引 React，五条都能在命令行里验完；**跑不起来本身就是"core 已经缠上 UI"的信号**。

#### 阶段一的实现约定（v6 补，实现时定死）

| 项 | 约定 | 为什么 |
|---|---|---|
| 运行方式 | Node ≥ 22.6 **直接跑 `.ts`**（type stripping），不引构建链 | 零依赖、启动快；AI 生成的目标越小越准 |
| **类型检查是独立环节** | `node --test` **不做类型检查**（只剥类型），必须另跑 `tsc --noEmit` | 实测漏掉过 2 处类型错（`child_update` 缺 `from`、残留类型名），**测试全绿也照漏** |
| `tsconfig` 开 `erasableSyntaxOnly` | 拦住 `enum` / `namespace` / 参数属性 | 这些语法 Node 剥不掉，会直接运行失败 |
| frontmatter 语法 | 每行 `键: <JSON 值>`；`content` 只走正文 | `JSON.parse` 不需要处理"引号里的冒号"，正确性优先于好看 |
| frontmatter 严格性 | 缺字段 / 未知键 / 类型不符 = **数据损坏**，直接抛错 | §4.3 的断言全建立在"文件忠实反映状态"上，补默认值会让损坏静默传播 |
| `card_create` 的落点 | 不带插入下标 → 挂在父卡 **children 末尾** | 事件结构里确实没有这个下标；要插到中间就再发一条 `child_update` |
| `updatedAt` | **v7 反转**：改为**派生量** = "指向这张卡的最后一条事件的时间"，由 `applyEvent` 统一推进；`field_set` 不许直接改它 | 原决定（v6）是"不隐式更新，要改就显式发 `field_set`"，顾虑是"隐式魔法会让同一串事件依赖上下文、重放不再是纯函数"。**这个顾虑在本实现下不成立**：新值只取自**事件自己的 `timestamp`**，不读任何环境状态，所以重放仍是纯函数。而原方案实测的结果是"谁都不去发那条 `field_set`" —— 字段永远等于 `createdAt`，等于一个骗人的字段 |
| 状态构造 | `children` 与 `cards` 都不留空壳（不变量 C） | 见 §2.8 |

#### 实现状态（v6 收尾：阶段一已完成）

代码落在 `src/core/`（**无 React 依赖**）与 `src/mcp/`。五条断言各有对应测试：

| 断言 | 落在 |
|---|---|
| 一 · 重放一致性 | `test/replay.test.ts`、`test/acceptance.test.ts` |
| 二 · 撤销正确性 | `test/undo.test.ts`、`test/acceptance.test.ts` |
| 三 · 崩溃一致性 | `test/storage.test.ts`、`test/acceptance.test.ts`（逐个写点崩一遍） |
| 四 · 存取往返 | `test/storage.test.ts`、`test/acceptance.test.ts` |
| 五 · MCP 通路 | `test/mcp-tools.test.ts`、`test/mcp-server.test.ts`（走真协议，不是直接调函数） |

一条命令验完：**`npm run check`**（= `tsc --noEmit` + `node --test`）。
**类型检查不能省** —— `node --test` 只剥类型、不做类型检查，实现期实测漏掉过类型错。
入口：`npm run mcp -- <工作区路径>` 起 stdio MCP 服务器。

**构建（v6 补）**：`npm run app:build`（= `tauri build`）真能出可执行文件。

```
kankanban.exe   3.01 MB     # LTO + opt-level="s" + strip
dist/                       # beforeBuildCommand 跑过：index.html + css + js
二进制内嵌前端   ✓          # 前端资源打进了 exe
ProductName      KankanBan / 0.1.0
```

> **`cargo check` 不等于能构建。** 它只做类型检查，链接、`tauri.conf.json`、
> capabilities、图标、`beforeBuildCommand` **全都没验**。应用曾经只跑过 `check`，
> 直到这一轮才第一次真正 build 出来 —— 这类"能检查不能构建"的问题，
> 只有真跑一次构建才发现得了。

### 阶段一·五：垂直切片（本版新增）

**目标**：在开始铺 UI 之前，先用最薄的一条通路压到数据模型的形状。

## 十三、风险与边界

**最大风险：范围膨胀。** 阶段一到三已经能构成完整课程作业。阶段四的 git 集成若时间不够，
降级为"导出 Markdown 文件夹"（§6.1 已把它定为常规协作通道，正好是这条降级）。

**窗口层风险：已大幅消除。** 三个透明无边框置顶窗口的共存、手动拖动、点对点事件、
深色模式黑边、程序化改尺寸、建窗死锁、**边缘吸附**、**右下角把手调整大小**、
**折叠为标题栏**——这些在 `sticky-tauri` 原型里都已**由用户实机确认**（逐项清单见
`sticky-tauri/DEVELOPMENT.md` §9「验证状态」）。原型已无遗留缺陷。
**把该原型的坑清单直接并入本项目，不要从零重验。**

> 具体已验结论（Tauri/Tao 源码级）：`shadow(true)` 会给无装饰窗口加 1px 原生边框（深色模式下是黑边），
> 需 `.shadow(false)`；同步命令跑在主线程，建窗会死锁，必须 `async fn`；
> 事件点对点投递要求发送侧 `emit_to` 与监听侧注册自己的 label **成对处理**；
> `outer_size()` 比请求的 `inner_size` 大一圈；`set_inner_size` 不检查 `RESIZABLE`。
>
> 吸附的完整语义（阈值 `max(10px, 较大宽度/25)`、平行轴严格重叠、拐角放行、屏幕工作区边缘）
> 与吸附的**时机**（拖动中只提示、松手才落位）都写在 `DEVELOPMENT.md` §6 / §7.16，
> 本项目直接沿用，**不要重新发明**。

> **折叠交互也是已验资产**：便签折叠成标题栏、以及折叠↔展开时保住用户调过的尺寸
> （`DEVELOPMENT.md` §7.17 末尾），都已实机确认。
> 唯一的保留：折叠按钮**早期失灵过一次，根因没定位**，靠 `z-index:1` 经验性修好的——
> 所以照搬它的**行为约定**（例如折叠高度实测、还原用 `NoteData::width/height` 而非常量），
> 但别把那次修复当成"已理解的机制"。

**交互风险：三区域布局、拖拽手势、下钻与浮动的区分** —— 需要实际用一下才能确认。
所以新增了阶段一·五的垂直切片，建议在阶段二就找一个人试五分钟。

**数据风险：文件存储的并发写入与原子性。** §4.2 的 WAL 协议已给出答案；单用户场景下够用。

**课程作业提醒**：老师大概率会问"你怎么知道它好用"。阶段五的一手观察比功能列表有说服力。
早期发现的问题改起来便宜。

**多人同步移除后的影响**：`scope` 已收敛为一条**纯派生规则**（§2.6），它就是同步层要用的规则，
落地时不必改数据布局；事件日志为同步预留增量流接口。
编辑标注、写锁、冲突提示在阶段一至五不实现，但数据结构上留好位置。
